## 1. MVP 的目标和完成定义

### 1.1 一条能真正运行的只读闭环

用户在已有 S01 界面选择获准店铺/仓/SKU 与分析时点，提交分析；后端受理持久任务，独立 Worker 获取经过授权和标准化的固定输入；S01 调用 B01 计算基线、调用 B02 生成并评价补货候选，保留数据与质量限制；O01 发布可重读的报告；用户从现有列表/详情查看数量、日期、逐日曲线、假设、阻断及证据。

“真正运行”包括真实的应用进程、MySQL 持久化、规则计算、任务恢复和 API 对接；不能把固定样例数字换一个任务 ID 就当运行结果。数据是否来自真实 ERP 另行标明，测试样例通过不能证明企业数据或生产条件已就绪。

MVP 到只读报告与人工复核结束。不存在真实建议确认/提交审批、批准或采购执行。前端沿用现有页面和设计规范，审批区域保持未启用；不能把原型角色切换或会话审批当作正式实现。

### 1.2 最小范围建议

| 维度 | MVP 保留 | 限制与理由 |
|---|---|---|
| 场景 | 只生产注册 S01；使用统一 ScenarioHandler 契约 | 不为跑通工程先实现 S02；其他场景不建空 Handler |
| 试点范围 | 一个经确认的租户/试点范围；支持从授权列表逐个选择 SKU 分析 | 模型保留 tenant/store/warehouse/SKU 维度；首版可一次只分析一个 SKU，不提前做批量调度 |
| 数据 | 调查后选定的一个实际主数据路径；模拟 fixture 供必要测试 | 不把三种来源都做成完整产品；不要求接齐所有业务系统 |
| 计算 | 可售、给定需求下逐日余额/首缺/缓冲缺口；MOQ/倍数/日期候选与 B01 评价 | 企业口径须冻结；无数据不强做学习预测、价格优化、多供应商求解 |
| 流程 | SINGLE，S01 内顺序 Workflow；可查询、可取消、可重启恢复、可重读报告 | 保留 participants 数组与版本；不启用 JOINT 执行、运行中交互暂停或自主 Loop |
| 交互 | 原型工作台、列表、详情与证据反馈接真实后端；审批入口显示未启用 | 不重新画页面，不迁入未经选择的 React/Vue 工程 |
| AI | 默认规则报告；A01 解释为可选增量 | 没有模型也能完成本 MVP；若明确将解释列为交付项，才增加其必要能力与用途验证 |
| 协同/写入 | 仅输出候选和人工复核事项 | C01/C02/C03 不注册、不建表、不排执行工作项 |

“只用部分底座”指只实现这些模块被 S01 用到的窄能力。它不等于删去权限、快照、证据或可靠投递，也不等于先把所有 A/B/C 阶段完成。模块责任完整，功能范围可以很小。（PLAN §2/5；ADR-MIN-001）

### 1.3 两种验收结论必须分开

| 可交付结论 | 必需证据 | 不能声称 |
|---|---|---|
| 工程/离线演示闭环可用 | 测试输入 + 真实 MySQL/API/Worker/计算/页面，明确 simulated | 真实 ERP 可用、企业规则已签认、生产上线或收益成立 |
| 真实 ERP 只读试点可用 | 以上工程证据 + 获准来源/字段映射/覆盖/时效/业务预期与人员复核 | 所有数据域已接通、采购已获批、生产容量/准确率/收益已达标 |

如果 ERP 满足条件，正式开发优先交第二种路径；第一种仍作为测试和离线备用证据，而不是必须先交付的独立模拟产品。

### 2.2 首版不启用的能力

A01/A02/A03、RAG、Function Calling、Skill/Runtime/Loop、长期 Memory、多 Agent、C01/C02/C03、Redis、Milvus、Neo4j、MQ 和响应缓存均不因“完整平台以后需要”而提前创建。缓存 OFF 时不建表、实例、清理线程或失效通道。

### 2.3 与既有 A/B/C 计划的关系

沿用 A-01—A-06 中与当前切片有关的契约/工程/身份/存储/投递和故障要求；沿用 B-01—B-05 的 S01 实际子集。它们是既有能力工作的引用，不要求先完成各模块的全量产品。B01 指标、B02 候选与 S01 的真实场景联调可以沿依赖逐步形成闭环，不等待 S02 或所有 AI 模块。

## 4. 可替换数据适配层

### 4.1 一条公共处理链

无论来源是什么，进入的链路都保持：

> 来源读取 → D01 批次/覆盖 → D02 映射与版本投影 → D03 质量与固定 manifest → S01 → B01/B02 → D04 证据引用 → O01 报告 → 现有 W01 界面。

读取适配器解决“怎样取得来源数据”，不计算补货、不发布报告、不直接写分析指标。标准化解决“来源字段怎样对应业务身份/单位/状态”，不能把标准化规则藏进前端或 B01 的 ERP 专用分支。替换来源时 B01/B02/S01/O01 的公开契约和公式保持稳定。

### 4.2 SourceConnector 的最小语义

沿用需求 §8 的 `SourceConnector.read(cursor, scope)` 与概要 §5.1 的 D01 用例。以下是待冻结的语义字段，不是本轮生成的接口实现或新 SDK。

| 项目 | 所有者与最小内容 | 不变量 |
|---|---|---|
| 读取请求 | D01：sourceId、domain、可信 scope、读取/观察窗口、游标与选用连接配置引用 | 调用方不能传任意 URL、SQL、文件路径或凭据；只用已登记来源 |
| SourceBatchRef | D01：tenant/source/domain/batchId、适配器版本、读取方式、源记录/版本引用、批次观测时间 | 批次可定位到保留期内的授权输入；hash 不能代替内容/版本 |
| 覆盖声明 | D01：requestedScope、实际覆盖、coverageThrough、分页/删除/失败与读取限制 | observedAt 很新不等于业务数据完整/新鲜；分页中断不标全量成功 |
| 来源类型 | 按数据域/资产记录真实 ERP、受控文件或 simulated fixture，供 D02/D03/报告引用 | 不能只用一个全局布尔值掩盖混合来源；模拟不能在标准化后丢标记 |
| 技术结果 | 成功、部分读取、明确失败及可重入性/剩余游标等语义 | 超时不转“零库存/无供给”；仅 D01 按原期限/预算处理技术读取重试 |
| 适配器装配 | 组合根按配置装配获准实现，提供相同批次语义 | 无法获取真实数据时不能静默回退模拟并伪称 ERP 成功 |

业务“只读”不等价于机械限制 HTTP GET：某些来源可能以 POST 查询。只有下一阶段调查证明其用途不产生业务写入、范围可控后，才列入明确的读取白名单；当前不假定任何具体端点安全。

### 4.3 三种来源的实现边界

| 来源实现 | 何时需要实体实现 | 最小实现方式 | 明确不做 |
|---|---|---|---|
| ERP 只读适配器 | 调查满足条件时为正式开发首选 | 一个获准范围内的读取适配器；按已验证接口实现分页/限流/版本/覆盖；凭据仅服务端 | 不先开发全厂商 SDK，不写采购/库存/单据，不模拟源幂等/版本能力 |
| 受控文件适配器 | 经调查决定用于合法导出或补充领域时 | 只支持实际选定的单一格式/Schema；记录提交人、版本、范围、水位与校验；文件入口可先为受控 CLI | 不开发通用上传/清洗平台，不允许服务器任意路径读取，不将文件当新业务主账 |
| fixture 适配器 | 自动化测试与必要离线演示 | 最小静态输入集，经 D01/D02 公共链处理；异常通过测试 fixture/故障注入构造 | 不建模拟 ERP 服务、订单生命周期或模拟采购系统；不把原型8个SKU全部扩建成业务数据库 |

“支持替换”通过稳定端口与消费者契约证明，不要求首版同时实现全部真实来源及 UI 文件上传。若三者均确有当前用途，分别实现三个窄读取器；不能为未选择的用途提前建空服务。

### 4.4 批次、去重与质量

同一来源批次重放不重复累加。来源身份至少在租户/来源域内唯一，具体复合键依据调查；没有可靠源版本时记录批次/内容指纹及其限制。D02 暴露不可变投影修订，成功提交后才推进可分析游标；读取到一半或存在隔离记录时如实影响 coverage。

ERP/WMS 库存镜像由已确认的权威/映射策略选择，不能相加。已收货部分不能继续当未收供给。供给重复、负剩余、单位冲突、删除或补录的具体规则必须经来源与业务口径确认；AI 不得为“使样例跑通”静默截零、去一行或改状态。

批次是否真实、输入是否质量通过、业务是否允许给采购候选是三个不同维度。真实 ERP 批次也可能因过旧或缺信号而阻断；模拟批次通过检查也仍是模拟。

## 5. 标准输入与领域契约

### 5.1 S01 最小标准输入

本表是 AI 应落实的业务语义；最终字段名/精度/可空性在开发准入时冻结，ERP 字段对应关系留待下一阶段调查。不得将表中逻辑名称说成 YAML 已提供的字段。

| 标准输入组 | 最小语义 | 缺少时的处理 |
|---|---|---|
| 范围与单位 | tenant/store/warehouse/canonicalSku、数量单位、审核映射版本 | 受影响对象不参与可靠计算；不能同名合并或跨租户读取 |
| 库存 | 已确认可售值或互斥分桶、sourceUpdatedAt、源记录版本、来源权威 | 无法可靠转换则阻断库存与采购结论，保留原因 |
| 需求事实 | 已确认历史口径、窗口、取消/退货适用规则与覆盖、预留对应关系 | 不把出库量、订单量、销售额等随意替换；口径不明不预测 |
| 给定未来需求 | 有单位的逐日新增需求曲线、截止日、来源/算法/参数版本、显式假设标记 | 可先有获准固定情景；无曲线依据不给首缺日和候选 |
| 未收供给 | 行/批次身份、状态、未收量、目的仓、预计可售日与证据 | 不把已收货、未知状态或重复供给计入确定可用量 |
| 候选约束 | MOQ、订购倍数、适用单位/供应商/有效期、可售日期依据及实际其他硬约束 | 缺必需约束不给可复核采购候选；未知不等于无上限 |
| 质量依赖 | required/optional 策略与版本、获准信号引用、适用范围/时效/调查条件 | required 缺失或矩阵未冻结时阻断质量安全及采购适用结论 |
| 来源与质量 | 每域来源类型/批次/观测/覆盖、不可变修订、缺项和质量版本 | 报告与证据保留真实限制；不能以一个latest引用代替固定输入 |

当前需求范围只需要单 SKU 的最小输入，不强制重建所有订单/采购/库存主表；保存能支撑当前计算和回源的最小投影及授权证据即可。

## 6. 业务计算、质量门禁与报告语义

### 6.1 不在实施文档另写第二套公式

可售公式沿用需求 §9.2：仅在分桶可靠且互斥时，B01 计算 `available = onHand − reserved − frozen − unusable`。ERP 若已返回净可售，不再扣一次。未来供给只计符合条件的未收部分，在预计可售日进入评价；已预留需求不能再作为新增需求重复扣减。其他逐日/缓冲/需求积压等语义沿 S01 专项 §4.2、§7，由相应版本化指标/策略冻结。

在正式编码前，当前切片必须明确以下规则集，而不是让开发 AI 临时选一条常见公式：

| 规则集 | 需要冻结的内容 | 责任 |
|---|---|---|
| 身份/库存 | 分桶互斥或净值语义、镜像/权威来源、单位/精度、负值处理 | D02/D03/B01与业务人员 |
| 需求 | 历史口径/截止/窗口、日新增与预留的关系、未来曲线及假设 | B01历史口径、B02未来需求 |
| 时间 | asOf到业务日、日初/日末、同日供给/需求先后、窗口/缓冲端点、到港到可售的依据 | B01时间评价、B02日期情景 |
| 供给 | 状态白名单、未收部分、分批/取消/删除/重复、过去预计日期仍未收 | D02映射、D03质量、B01给定输入评价 |
| 候选 | MOQ/倍数单位和聚合范围、零采购情景、可售日期、其他硬约束、比较维度 | B02；不编造目标权重/价格或供应承诺 |
| 质量/降级 | required/optional、各域时效/覆盖、调查条件、何时仅基线/局部/阻断 | D03检查、S01领域限制、O01整体完整性 |

真实 ERP 可读不代表这些规则已冻结。示例专用策略可以被单独评审用于测试/离线演示，必须在结果中保留 simulated/假设标签，不能自动成为企业生产政策。

### 6.2 S01 Workflow 的实现约束

| 处理阶段 | 做什么 | 异常终点 |
|---|---|---|
| 输入/质量 | 在固定manifest中读取范围、投影、质量与版本；核验当前权限/取消/期限 | 无法固定输入不伪造snapshot；库存/映射/重复使供需不可靠则阻断相应结论 |
| 需求/基线 | 显式需求情景可直接作为假设；需预测才由B02生成曲线；B01评价基线 | 无需求曲线只保留有依据的当前指标，不虚构未来首缺/缺口 |
| 候选 | 质量与必要约束合格时B02构造有限候选，每个调用同版本B01 | B02不可用只留可靠基线；无解不等于无需补货；不让LLM松硬约束 |
| 门禁/摘要 | S01组合供需、约束及质量限制，形成固定规则解释和证据Refs | required质量缺失/调查条件成立，保留事实但阻断采购适用性；缺证据不放行 |
| 返回/发布 | Handler返回DomainResult，O01审校版本/证据并发布不可变报告 | 旧plan、失lease、取消、超期、撤权或存储失败不发布迟到结果 |

首版不实现 Runtime/YIELD 等待基础设施。用户补证或供应日期改变后，明确提交关联旧报告的新分析，产生新的输入/计划/报告关联；不复活终态任务、不覆盖历史指标。只保留O01既有受控重规划的契约兼容性，不为未选用的运行中重规划提前建完整引擎。

### 6.3 报告状态与技术状态

O01 Task State 仍为 QUEUED/RUNNING/SUCCEEDED/FAILED/CANCELLED；I01 投递状态仍只描述工作项；报告 COMPLETE/PARTIAL/RULES_ONLY/BLOCKED 描述业务完整性。这三者不能混写。

实施建议：正常发布一份明确的 BLOCKED 说明可以按 O01 已有语义视为技术处理成功；必须同时让界面显示业务阻断。取消或未发布的任务不得有假报告入口。无模型时，按签认的完整性矩阵标规则报告，并另列依赖和阻断；不能用 RULES_ONLY 掩盖 required 质量缺失。具体状态组合在当前契约冻结时确定，禁止前端自行推断。

报告最少包含：范围/时点/窗口/单位，逐域来源类型和覆盖，基线指标Refs，候选及评价Refs，基线与候选逐日曲线，假设/约束/未解决风险，质量与数据缺口，当前可访问证据，task/plan/participant/snapshot/report和相关策略版本。金额/币种/报价未知时不显示虚构货值或“最经济”排序。

沿用概要设计的 Python/FastAPI、MySQL、SQLAlchemy/Alembic 和模块化单体方向。API 和 Worker 必须是独立进程，同一制品在各自进程装配相同模块的不同用例。不是 Worker 经 HTTP 回调 API 才能运行 O01；不是每个逻辑模块一个微服务。

| `src/commerce_hub/bootstrap/`、`entrypoints/http/`、`entrypoints/worker/` | 配置/组合根/入口；只注册已实现能力；API启动不自行迁移、不启动Worker |

### 7.2 需要持久化的最小逻辑资产

下表定义唯一所有者，不是要求一行对应一张表，也不是完整 DDL。实际表/索引只覆盖当前已选路径，采用同一迁移链；不得合并资产责任或用大 JSON 藏关键状态/租户/索引条件。

| 所有者 | MVP 逻辑资产 | 唯一性/版本重点 |
|---|---|---|
| D01 | 来源配置引用、读取批次/覆盖、实际需要的游标 | 不存明文凭据；同来源批次重放有据可去重 |
| D02 | 当前映射与投影修订、来源定位/删除信息 | tenant与来源身份、单位、状态、immutable revision |
| D03 | 质量检查、snapshot与输入manifest | 固定到已提交版本；不覆盖旧manifest |
| D04 | 证据Ref与必要血缘关系 | 资产/版本/locator/权限；只引用生产者结果 |
| B01 | 当前指标定义版本和metric result | 输入/情景/口径/单位/窗口和结果版本 |
| B02 | 当前需求情景、候选/约束与评价Ref | 不再保存一套可修改逐日指标 |
| O01 | task、固定plan/participant run、报告、当前有效运行限制 | 命令去重、当前plan/版本、不可变report与发布去重；无模型时无需预建计费全表 |
| I01 | work item与必要attempt/lease | 工作种类/去重/到期/lease fencing；不存第二份领域状态 |
| G01 | 当前采用的身份绑定/范围策略 | 具体发行方与浏览器会话待冻结，不建完整用户管理产品 |
| G02 | 必需审计与最小trace/失败/版本关联 | 不复制输入/指标/报告正文为另一权威 |

数量按单位用精确类型，金额若有才用 Decimal/币种及口径；tenant参与键与关联约束；时间按概要约定保存UTC并保留源时区/业务日。共享物理MySQL不允许跨模块私写表或共享任意ORM。

### 7.3 必须有的事务与去重

| 用例 | 原子边界 | 崩溃/重复处理要求 |
|---|---|---|
| 受理分析 | O01任务/初始计划 + I01投递 + 必需审计同一短事务 | 失败全回滚；同租户/主体/命令key同内容返回原引用，不同内容409；查询重放仍校验当前权限 |
| 批次可分析 | D02投影修订与处理标记、对应可分析游标提交一致 | 只读网络/文件读取在锁外；半批不得暴露为完整输入 |
| 冻结snapshot | D03 manifest/质量关联完整提交 | 不能出现半份清单，也不能通过长期数据库读事务代替永久快照 |
| 保存指标/候选 | 各生产者按输入/版本/逻辑步骤键保存或识别已完成产物 | Worker重入不无限堆新产物，兼容条件不满足则重算/阻断而不是改旧资产 |
| 发布报告 | O01检查当前plan/lease/取消/权限与证据后追加报告、任务收尾和必需审计 | 重复投递不能重复发布逻辑报告；失去租约者不能覆盖新运行；发布失败没有假报告 |

跨模块顺序命令共享一段已装配事务上下文，各模块仍经自己Repository写自己的资产；不能每层Service各自commit。并发分支用独立Session。来源/模型网络请求和证据外部解析在锁外，发布时再次做本地条件核验。

### 7.4 Worker 恢复的最小实现

I01 只分派已注册的 O01 分析用例或当前必要数据读取用例，不接受 Python导入路径、pickle、任意脚本。MySQL队列式领取/租约沿概要 §11；心跳/完成/重排/发布均带当前lease条件，用数据库时间判断过期。

MVP 不需要通用 Agent 检查点平台。O01可保存当前参与者阶段和已完成产物Refs，按固定Workflow的安全边界恢复；重入先检查终态、取消、deadline、当前授权、版本、有效产物和未决调用。任务deadline和已用资源不因重启重置。首版顺序执行，长读取受受控超时/有界重试限制；是否需要独立心跳执行及其Session，在实际单步耗时/租约验证后确定，不能把锁一直持有到网络返回。

取消是协作式的：排队项阻止启动，运行项在安全边界停止新步骤；已经返回的迟到产物不得复活任务。至少一次投递通过业务幂等和条件发布保证不重复产生逻辑报告，不承诺跨系统 exactly-once。

## 8. 最小 API 与页面数据契约

### 8.1 资源范围建议

沿用概要 §6.3 的资源方向；列表、选项和证据读接口为当前真实消费者需要的细化建议，应在开发前的最小契约评审冻结。这里不是本轮新建 OpenAPI 或调用接口。

| 资源 / 方法语义 | 归属 | MVP 行为 |
|---|---|---|
| 创建分析：`POST /api/v1/analysis-tasks` | W01→O01 | 服务端鉴权/范围/参数/去重，持久受理后返回202、taskRef和Location |
| 查询分析：`GET /api/v1/analysis-tasks/{id}` | O01 | 技术状态、受限进度/原因、关联的已发布reportRef；无报告不伪造ID |
| 取消分析：`POST /api/v1/analysis-tasks/{id}/cancel` | O01 | 明确用户命令、幂等与状态核验；不是立即回滚所有正在进行的读取 |
| 报告列表/详情：`GET /api/v1/reports`、`GET /api/v1/reports/{id}` | O01公开读口 | 只读已发布有权版本；以报告/结果数据呈现现有建议列表和详情，不创建C01建议 |

| 分析选项：受控S01 options读用例 | W01组合G01和D02公开读口 | 只给有权且有映射的店铺/仓/SKU/单位；具体URI在契约冻结时确定，不开放通用查询引擎 |

没有用于建议确认/审批/执行或任意自然语言工具调用的生产路由。未知/未实现能力明确不可用，不能返回固定成功对象占位。初版轮询足够，不强制SSE/WebSocket。

### 8.2 请求与响应的必要约束

| 类型 | 最小语义 | 服务端约束 |
|---|---|---|
| 分析请求 | 用户选择的store/warehouse/SKU、asOf与获准业务窗口/参数、命令去重key | tenant/principal/有效scope由服务端绑定；不接受客户端自签policy、snapshot、plan或required质量降级 |
| 任务查询 | taskRef、Task State、必要进度、可见错误/限制、已发布reportRef | task与report完整性分开；YIELD/未发布/取消不出现假报告入口 |
| 列表视图 | 实际对象/单位、基线可售/首缺、候选量或不可用、阻断类型、report与输入关联 | 不使用固定“4项/8SKU/55/20”；无候选和未知显示明确原因，不填0 |
| 详情视图 | baseline/candidate分列、逐日值/日期、约束/假设、风险/缺口/证据/版本 | 前端只绘图/格式化，数量与日期由B01/B02资产引用提供，不在浏览器重算 |
| 错误信封 | code/message/details/traceId/retryable | details脱敏；401/403或统一404、409、422沿概要；受理后的业务结果由查询表达 |

同源 API/静态页面优先，避免为当前 MVP 新建前端网关。浏览器认证必须在开发准入时选定：企业已有身份优先复用；如用本地测试身份，也要验证签名、发行方、时限并经过 G01 当前策略，不采用“前端角色下拉框=真实身份”。浏览器会话存储、Cookie/CSRF或其他认证传输、安全边界由 G01 与 W01 一起冻结；缺配置拒绝启动相关访问，不降为匿名。测试令牌/秘密不写入 JS、Git、URL或日志。

### 8.3 MVP 请求的有限性

默认只受理一个 SKU 的 SINGLE S01。窗口/记录数/候选数/任务时间/重试必须有显式配置上限，数值在实际样本/调用约束验证后冻结，不写“无限”。参与者不是S01、未经允许的JOINT、任意来源URL/路径、越界scope和未获准参数都拒绝。

普通用户不能在请求里伪造质量通过、把库存改成55或指定“正常/延期/模型失败”控制服务器结果。测试和离线演示需要的异常注入只在测试装配/获准fixture配置中启用，不暴露为真实ERP生产API参数。

### 12.2 后续 AI 的工作方式

先核对当前 Git 和授权，读取本文适用段落以及接口调查后的修订差异，再处理当前获准实现范围。遇规则缺失/源语义冲突，明确影响及可用结论，不用LLM或常见行业公式填企业事实；能独立推进的工程部分按当前授权推进，不把全平台未知变成所有工作的统一阻碍。
