- 日期：2026-11-14 · 分支 `review/workbuddy-s01-ux`
- 配套原型：`prototypes/s01-workbench-v3/index.html`
- 前置阅读：`docs/reports/S01_UX问题清单与代码定位_20261114.md`

## 1. 设计出发点：采购运营一天在做什么

现有页面按"系统有什么数据"组织；本次改为按"人要做哪几件事"组织。一天的真实节奏是：

1. **早上看一遍**：昨天到今天有没有新增的断货风险、有没有新的数据问题卡住了判断 → *工作台*
2. **逐条判断**：哪些要补、补多少、依据是否站得住 → *补货建议 → SKU 详情*
3. **把决定办掉**：确认数量、提交请购，然后盯着 ERP 那边批没批 → *SKU 详情操作栏 → 请购管理*

这三步对应三种不同的注意力："扫 → 判 → 办"。任何一步都不应该被另外两步的内容打断。现有实现把三者压在一页，正是 P2/P3 的根源。

## 2. 四个业务入口

| # | 入口 | 回答的问题 | 主对象 | 关键动作 |
|---|---|---|---|---|
| 1 | 工作台 | 今天我要处理什么 | 待办集合 | 点卡片带着筛选跳转 |
| 2 | 补货建议 | 全部授权对象现在什么状态 | 店仓对象列表 | 搜索/筛选/打开详情 |
| 3 | SKU 详情 | 这一个该不该补、补多少、凭什么 | 单个店仓对象 | 确认数量、提交请购、看依据 |
| 4 | 请购管理 | 我提交的单子到哪一步了 | 请购单 | 看待审批/已审批/待核对、原单核对 |

### 2.1 关于"SKU 详情"是否作为顶级导航

严格按字面，四个入口应该是四个平级导航项。**本次没有这样做**，理由：

- `SKU 详情` 必须绑定一个具体对象才成立。作为顶级导航项，用户点进去只能看到"请先选择一个 SKU"的空态，是一个死入口。
- 业界同类产品（Shopify 商品详情、Amazon 卖家后台的 Listing 编辑）都把对象详情做成列表的下钻页，而不是一级导航。

**采用的方案**：3 个常驻导航 + 1 个上下文导航。

```
补货建议              ← 常驻
  └ SKU 详情 · CB-1001   ← 打开某个 SKU 后出现在其下，带 aria-current
请购管理              ← 常驻
```

这样"四个入口"在视觉与可点击性上都成立，同时不产生死入口。**如果负责人坚持四个平级导航**，替代方案是第四项显示"最近打开的 SKU"，空态时列出最近 5 个对象供选择——但会多一次跳转，且与列表重复。请评审时明确取舍。

### 2.2 与 `docs/ui/PRODUCT_SPEC.md`（v0.2）四页的差异

| 旧 | 新 | 变更理由 |
|---|---|---|
| 工作台 | 工作台 | 保留。去掉装饰性趋势与 hero 宣传，改为"待办计数 + 优先处理队列 + 数据状态" |
| 补货建议列表 | 补货建议 | 保留。增加"建议来源"列（规则 / ERP 参考 / 无来源）与处理状态分段筛选 |
| 建议详情 | **SKU 详情** | 升级为独立路由页。由"报告详情"改为"对象详情 + 操作栏"，因为补货判断的对象是店仓 SKU，不是那份报告 |
| 人工审批 | **请购管理** | 改名。平台无审批权（P3 契约明示），原名会让运营误判；新页管理"已提交请购及其 ERP 状态" |

## 3. 路由与可恢复状态

原型已按此实现（`#/` 前缀为 hash 路由，正式前端改用 Vue Router 同结构）：

| 路由 | 页面 | 可分享 | 说明 |
|---|---|---|---|
| `/workbench` | 工作台 | 是 | 默认入口 |
| `/suggestions` | 补货建议 | 是 | 筛选写入 sessionStorage，刷新保留 |
| `/sku/:entityKey` | SKU 详情 | 是 | 分区 `?tab=sales` 可深链 |
| `/requisitions` | 请购管理 | 是 | 状态分段 `?state=waiting` |
| `/requisitions/:no` | 请购单详情 | 是 | 单据号用业务号，不用 UUID |

**三条硬要求**（原型均已实测）：

1. **返回保留筛选**：从列表进详情再返回，筛选、搜索词、滚动位置都不丢。
2. **浏览器后退可用**：每次页面切换都是真实 hash 变更，后退回到上一页而非上一标题。
3. **刷新可恢复**：列表筛选存 `sessionStorage`（会话级，不是业务持久化）。

## 4. 状态模型：把"技术状态"翻译成"处理阶段"

现有实现把 `analysisState`（7 个枚举）、`sourceGrade`（5 个）、`procurementEligibility`、`requisition.state` 全部平铺给用户。新设计分两层：

**第一层：建议来源**（这个数字从哪来）

| 值 | 界面文案 | 含义 |
|---|---|---|
| `RULE_CALCULATED` | 平台规则计算 | B01/B02 完整计算，可确认 |
| `REFERENCE_ONLY` | ERP 参考建议 | 数量来自 ERP，计算依据未验证 |
| `NONE` | 无可用来源 | 数据不足，未形成数量 |

**第二层：处理阶段**（我要做什么）

| 阶段 | 界面文案 | 可用动作 | 原型对象 |
|---|---|---|---|
| `pending_confirm` | 待人工确认 | 确认数量、提交请购 | CB-1001 / BT-2003 / CB-1023 |
| `need_evidence` | 依据待核实 | 补证后重新分析（不可提交） | LT-3012 / LT-3021 / KT-4010 |
| `no_need` | 无需补货 | 仅查看 | CB-1008 |
| `requisition_waiting` | 已提交 · 待 ERP 审批 | 查看请购单 | CB-1015 |
| `requisition_approved` | ERP 已审批 | 查看请购单 | BT-2020 |
| `requisition_check` | 提交结果待核对 | 原单核对 | CB-1030 |
| `failed` | 分析失败 | 重新分析 | KT-4022 |

技术枚举（`NEEDS_REVIEW`、`UNAVAILABLE`、`UNKNOWN` 等）只出现在「依据与限制 → 技术信息」折叠区。**来源与阶段是两条独立维度，不合并成一个分数**——这正是现有 `riskGroup` 想表达但被平铺掉的东西。

## 5. 数据质量状态：可扩展结构

负责人提出的"15 天内 7 个有效业务日"尚未确认，因此**不写进任何判定**，但要为它留位置。原型采用如下结构（与正式前端建议的 TypeScript 形状一致）：

```ts
type CheckLevel = 'BLOCK' | 'WARN' | 'INFO'

interface QualityCheck {
  code: string            // 稳定枚举，前端不解析文案
  level: CheckLevel       // 是否阻断
  title: string           // 一句话结论
  detail: string          // 事实描述
  owner: string           // 责任方（数据/质量/采购/系统）
  action: string          // 下一步
  affects: string[]       // 影响哪一部分结论：建议数量 / 可用库存 / 采购条件
  draft?: string          // 政策草案要求，明确标注"未生效"
}

interface AdmissionPolicy {
  id: string              // s01-admission
  version: string         // v0-draft
  status: 'DRAFT' | 'CONFIRMED'
  note: string
  draft?: { windowDays: number; requiredSalesDays: number }
}
```

**渲染规则**（解决 P6 重复警告）：

1. 一个 SKU 最多显示**一条**汇总提示（"N 项限制需要知悉"），标题列出前两项。
2. 阻断项与提示项分组，阻断永远在上。
3. 同一 `code` 在多处出现时只渲染一次（按 `code` 去重）。
4. `draft` 字段只以"政策草案 · 未生效"标签出现，**不参与**阶段判定；政策 `status` 变为 `CONFIRMED` 时，只需把该字段提升为 `requirement` 并加入判定函数，页面结构不变。
5. 每条检查都必须有 `owner` 与 `action`——只描述问题不给责任方的提示，运营无法处理。

## 6. 页面设计说明

### 6.1 工作台

**要解决的问题**：现有工作台把 hero 宣传、范围选择、指标、历史表混排，用户看完不知道先做什么。

**结构**

```
[页头] 采购运营工作台        [切换检查批次] [重新检查全部 SKU]
[数据状态条] 3 项依据待核实 · 本次检查 08:02 · 覆盖 11/11 · 覆盖率100%   批量不调模型  [查看全部结果]
[4 张待办卡] 待人工确认 3 | 依据待核实 3 | 请购跟进 3 | 无需补货 1
[左 2/3] 优先处理（最多6项，按"待核对 > 待确认 > 待核实"再按首次短缺日） 
[右 1/3] 数据范围与政策（含政策草案未生效） / 最近操作
```

**设计取舍**

- 待办卡可点击，点击即带筛选跳到列表——不是装饰卡片。
- 数据状态条只有一条，替代原来的 4 条 `Notice`；"不调用模型、不写业务"作为固定的能力声明放在条内右侧，不再每次弹提示。
- 不放趋势图：现有 `InventoryChart` 在 8 个指标旁边没有决策价值。
- 右栏"数据范围与政策"是**准入策略变化的唯一展示位**，将来政策确认后只改这里。

### 6.2 补货建议

**结构**：筛选区（搜索 / 店铺 / 仓库 / 来源 + 状态分段）+ 单表 8 列 + 页脚。

**列**：商品·SKU｜店铺·仓｜建议来源｜可用/目标｜建议数量｜首次短缺｜处理状态｜操作。

**设计取舍**

- **不显示任务 ID**。列表回答的是"哪个商品"，不是"哪个任务"。
- 状态用文字标签而非颜色块；`无需补货`、`未形成`、`—` 三种"空"必须可区分（分别是"算过且不需要"、"没算出"、"没数据"）。
- 空态给出恢复入口（清空筛选），不是一句"暂无数据"。
- 窄窗（<900px）：只对数字/日期/状态列禁换行，商品与店铺列允许折行，避免横向裁切；再窄则容器内横向滚动并给出提示。

### 6.3 SKU 详情

**结构**：返回 → 页头（名称/SKU/店仓/阶段/单位）→ 结论条（4 个数字）→ 左分区（5 个 tab）+ 右操作栏。

**五个分区**

| 分区 | 内容 | 为什么单独成区 |
|---|---|---|
| 概览 | 判定结论、为什么是这个数字、3 项事实卡（销量窗口/采购条件/在途）、限制汇总 | 30 秒内能下判断 |
| 销售与库存 | 有效销量窗口 + 逐日结存（含条形与负结存标记） | 数量争议时看这里 |
| 采购条件 | MOQ/倍数/报价/供应商/有效期 + 已有正式采购 | 提交前的硬约束 |
| 依据与限制 | 准入状态、质量检查（含责任方）、**数据来源与证据定位**、技术信息折叠 | 排查与审计 |
| 历史分析 | 该 SKU 的历史版本与结果 | 回答"上次为什么是 30" |

**右操作栏（sticky）**：平台建议量 → 人工最终量（步进器按整箱倍数增减）→ 实时约束校验 → 调整原因（仅改量时出现）→ 确认勾选 → 提交按钮。提交后整栏切换为"请购状态卡"。

**关键交互约束**（原型已实现并测试）

1. 数量不满足 MOQ / 整箱倍数 → 按钮禁用 + 就地说明，不用弹窗。
2. 改动数量但未填原因 → 禁用，提示"调整了建议数量，请填写原因"。
3. 未勾选确认 → 禁用。
4. 提交后不做"乐观成功"，直接进入"已提交 · 待 ERP 审批"，并保留平台建议量与实际提交量。
5. UNKNOWN 状态只提供"使用原单核对"，不提供再次提交。

**概念分离**（贯穿全站文案）

| 概念 | 谁产生 | 能否被平台修改 |
|---|---|---|
| 平台建议数量 | B01/B02 | 否 |
| ERP 参考建议 | ERP | 否 |
| 人工最终数量 | 采购运营 | 是（需填原因） |
| 平台人工确认 | 采购运营 | 是 |
| ERP 领导审批 | ERP 角色 | **否，只读回读** |

### 6.4 请购管理

**结构**：概念声明条 → 待核对提醒（有 UNKNOWN 时）→ 状态分段（全部 / 待 ERP 审批 / 已审批 / 待核对）→ 表格 → 详情页（4 步进度条 + 数量对比 + ERP 单据 + 操作记录）。

**设计取舍**

- 页面顶部常驻一句"平台人工确认 ≠ ERP 领导审批"，这是本页存在的理由。
- 单据号用业务号（`RQ-2026-0011`），回读时间以灰字附在单号下，不新增一列。
- 详情用 4 步进度条表达"已到哪一步、后面谁负责"，其中"下单与收货"明确标注"不在本平台范围"。
- **数据现状**：后端暂无请购列表接口（见问题清单 §4）。正式实现前，本页在原型中为演示态；上线策略见改造路线 P0。

## 7. 密度与响应式

| 断点 | 行为 |
