## 1. 改了什么

原来 `App.vue:59` 用 `<V2Workbench>` 抢占所有路由，导航只改面包屑；所有功能（批次、指标、表格、详情、历史、请购）堆在同一个长页面。本轮把这一个页面拆成四个真实路由：

| 路由 | 页面 | 数据来源 |
|---|---|---|
| `#/workbench` | 采购运营工作台 | `GET /s01/v2/batches/{id}` + `/items` 首页 |
| `#/suggestions` | 补货建议 | `/items` 服务端筛选 + 分页，筛选条件写在 URL |
| `#/sku/:entityKey` | SKU 详情 | `/items/{key}`；`?single=` 打开指定单品分析 |
| `#/requisitions` | 请购管理 | `/singles` + 逐条 `/singles/{id}/requisition` |

要点：

- **路由**：`src/router.ts` 用 60 行 hash 路由，URL 是唯一真源。前进/后退/刷新/返回筛选全部由浏览器行为保证，不用内存状态模拟。
- **数据层**：`src/s01.ts` 单一 store，所有数字来自 API；前端只做"服务端计数的分组展示"，不重算补货量、不推算销量、不造趋势。
- **布局 C**：SKU 详情为「结论条 → 智能分析 → 库存与销量图 → 采购条件/依据/历史 → 底部常驻操作条」。
- **AI 前置**：`AiAnalysis.vue` 覆盖未生成 / 生成中 / 已生成 / 未调用 / 失败五态；四段结构（结论 + 关键事实 + 风险 + 建议人工核实）直接映射后端 `explanation` 的四个分区，页脚固定写「AI 仅解释，不计算补货数量」。
- **图表**：只画后端能给的三类——结存折线（`supplyDemand.baseline.series`）、日销量柱（`forecast.dailySales`）、对象构成环形（汇总计数）。没有 `ruleResult` 就不画图，改列原因（`recoveryHints`）。
- **历史参考**：`HISTORICAL_REFERENCE` 单独成阶段，结论条写「历史参考 / 未形成 / 仅历史销量，不作建议」，操作条直接「暂不可提交」，不提供数量输入。
- **ERP 参考（方案 B）**：来源标 `REFERENCE_ONLY`，只要 `procurementEligibility.eligible` 且 `canSubmit` 就能人工确认提交，不因来源未知一律禁止。
- **请购**：提交必须基于一次单品分析（后端 `requisition` 绑定 single task）。因此详情页在无单品分析时给出「生成单品分析」，而不是假装可以直接提交；提交失败保留原幂等键，提供「使用原命令核对」。
- 删除已被替代的 `components/V2Workbench.vue`（旧单页工作台），旧 V1 界面保留在 `App.vue` 的非 V2 分支。

## 5. 接口缺口（需要后端/Codex 处理）

1. **请购列表接口缺失（P0）**：只有 `GET /s01/v2/singles/{id}/requisition`。当前"请购管理"按最近 20 条单品分析逐条回读，页面已明确写「不是全平台台账」。
   建议最小接口：`GET /s01/v2/requisitions?state=&erpStatus=&before=&limit=`，返回 `{items:[{operationId, taskId, sku, entityKey, platformState, erpId, erpNumber, erpStatus, aiQuantity, finalQuantity, verifiedAt, errorCode}], nextCursor}`。
2. **批次→单品关联**：`/singles` 已带 `entityKey`，但没有"该对象在本批次是否有单品分析"的字段；前端靠 `entityKey` 匹配，跨批次时会指向历史分析（现在用 `?single=` 显式打开，不再自动替换批次结论）。
3. **`V2Summary` 类型缺字段**：后端已返回 `ruleSourceCount`、`erpSourceRecordCount`、`productIdentityCount`，`api/v2.ts` 未声明；本轮未用，建议补齐。
4. **`observedAt` 粒度**：列表项的 `observedAt` 是采集时间，详情页"数据时点"直接展示它；若后端能区分"库存观测时间 / 报告生成时间"会更准确。

## 6. 已知限制

- 页面进入时 `GET /batches/{id}` 需要 3–6 秒（977 对象在线统计），已加"正在读取批次结果"状态；再优化需后端提供摘要缓存或分页统计。
- 列表每页 50 条，服务端筛选后仍要全量扫描；30 SKU / 60 天试点规模没问题，批次继续变大会变慢。
- 窄窗（<900px）隐藏"缺货日"列，详情页与工作台仍可见，这是主动取舍。
- 超管登录、一次性启动、CSRF/Cookie 逻辑完全复用原实现，未新增账号体系。
- 旧的真实流程 spec（`v2.spec.ts`、`local-platform.spec.ts`、`p3.spec.ts`）只做了选择器文案对齐，流程语义变化处（旧"查看单品历史"入口 → 现在"请购管理 → 查看 SKU"）需在下次真实验收时重新基线，本轮未执行这些需要私有令牌/回执的用例。

## 7. 与原型的差异（有意为之）

- 没有 A/B/C 布局切换器，直接落地 C。
- 没有模拟 SKU、伪造单据、前端推算数量或预测曲线；原型里的"覆盖天数/首次短缺"在正式版只在后端返回 `ruleResult` 时出现。
- 原型中"直接提交"的快捷路径不存在——后端要求先有单品分析，页面如实要求先"生成单品分析"。
- 政策"15 天 7 个有效业务日"未出现在正式前端。
