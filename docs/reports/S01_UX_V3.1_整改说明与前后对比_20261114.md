## 0. 一句话说明改动

把"教学展示型原型"改成"运营人员每天愿意打开的工作台"：删掉占屏的防御性说明，用**库存覆盖、状态分布、结存预测、销量柱、请购流转**这些有业务含义的图形承载判断；同时修掉 11 个真实缺陷，其中一个是**建议数量与目标库存算不相等**的数据矛盾，另一个是**提交后状态根本没有保存**。

## 1. 验收方式（本轮换了标准）

上一轮用 Node 模拟 DOM 断言 74 项"全通过"，但其中"提交请购"这条是**假通过**：断言匹配到的是右下角 toast 的文案"等待 ERP 审批"，而页面本身因为写在了派生副本上已经回滚。**这正是"Node 模拟 DOM 不能代替浏览器验收"的实例。**

本轮改用 CDP 直连 Edge：

| 项 | 做法 |
|---|---|
| 点击 | `Input.dispatchMouseEvent` 真实鼠标按下/抬起，按元素中心坐标命中 |
| 输入 | 逐字符 `Input.dispatchKeyEvent`，再派发 `input` 事件 |
| 断言 | `#main` 内文本与结构（**排除 toast**，避免上次那类误判） |
| 截图 | `Page.captureScreenshot`，三档宽度 `1440 / 1024 / 820` |
| 运行 | `node _e2e.cjs`（自动拉起 headless Edge，结束自动退出） |

结果文件：`_e2e-result.json`（63/63）。

## 6. 剩余限制

1. **请购列表接口不存在**。后端仅有 `GET /s01/v2/singles/{task_id}/requisition`（`s01_v2.py:122-127`），单品历史也不带请购摘要（`:106-114`）。原型中的"请购管理"为**演示态**；正式实现必须先补只读列表接口（见改造路线 P0），**禁止前端拼装历史冒充台账**。
2. **低记录数页面留白**。3 条请购单 / 筛选后 3 条建议时，表格下方为空。选择不填充虚构数据、不加装饰块，保留"列表到此结束"的阅读感。
3. **窄窗隐藏列**。<1000px 隐藏"首次短缺"列，该值在详情与工作台可见；这是主动取舍，不是缺失。
4. **演示数据规模**。11 个店仓对象、3 个批次、3 张请购单；批次差异只覆盖 3 个 SKU（其余沿用），不足以验证分页与大批量性能。
5. **未做**：批量确认、导出、审批动作（业务前提与权限模型未定）。
6. 原型不连接 ERP、不调用模型、不写任何系统；`演示数据` 角标与 `title` 说明是唯一环境标识。

## 7. 交接给正式前端的三条硬约束

1. **不要把说明文字写回页面**。环境标识进顶栏角标或"系统信息"，不占业务视野。
2. **图形只能映射真实字段**。本次五个图分别对应：`analysisState` 分组、`available/target`、`daily[].close/arr[]`、`sales[]`、`requisition.plat/erp`。前端不得自造评分、趋势或"健康度"。
3. **建议数量必须可与目标库存对账**。`目标 − 可用 − 有效在途 → 按 MOQ/整箱取整 = 建议`，任一环节不一致即视为数据缺陷，不得用前端四舍五入掩盖。
