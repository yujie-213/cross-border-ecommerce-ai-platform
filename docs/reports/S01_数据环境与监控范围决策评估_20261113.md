### 2. 数据模型、关系与经营逻辑

关系链为：**数据集 → 店铺/仓库 → 商品真实 ID 与 SKU → Listing 真实 ID → 销售明细；供应商真实 ID/编码 → 有效报价 → 采购单/行 → 送货/收货 → 库存批次/流水。** 同时保存 ERP 租户及每项所属关系；名称只作展示，不能作为唯一归属证明。

经营生成使用固定种子和经批准的商品生命周期、趋势、周内波动及订单分配；不是每条独立随机。价格、成本、单位、币种和数量精度一致，采购 MOQ/交期与报价有效期匹配；不创建真实客户、电话、地址或外部通知。

必须核对：期初数量 + 实际确认入库 − 实际确认出库 ± 已确认调拨/调整 = 期末实物量；净可售按已确认分桶解释。销售创建是否扣库、入库确认是否自动新增批次、单头未收量是否自动结转，都先在小试中验证。**若自动过账，就不能再人工创建一份相同库存。** 无可读流水时保留“完整因果链未通过”，不填一个总量伪装一致。

时间以批准导入日 T0 为锚点，历史覆盖 T0 前已结束的业务日。业务时区/日历明确，记录 UTC 观测时间；不将源 updated_at 当作销量覆盖水位。ERP 自动维护的 created_at/updated_at 不伪造；过期库存负例需要自然超过阈值后复测，或先使用允许填写的历史业务日期/缺字段负例，并分别标记未运行项。

未来需求曲线、独立订购倍数、到货后质检/上架等待和质量策略需要独立的教学规则版本。不能把历史销量直接当未经声明的预测，不能把 planned_arrival 当可售日，不能把 default_carton_qty 当倍数。历史到未来的情景构造仍归 B02，权威逐日评价仍归 B01；LLM 只解释。

可直接通过 ERP 声明字段保存的事实必须在那里保存并回读。ERP 缺少的规则字段，优先验证已有正式自定义字段能力；不支持时，用范围、单位、版本、有效期和负责人批准的受控教学规则作为**明确的第二来源**，不能声称是 ERP 原生事实，也不能因此解除企业门。

| DependentRefs | 供应商/报价 ID、采购单/行 ID、销售单/行 ID、收货/库存批次/流水 ID 及父子关系证据；没有明细独立 ID 时保存父 ID＋稳定行定位及内容摘要 |
| ScopeVersion | 不可变成员及关系清单、登记/激活时间、变更原因、批准人、停用/隔离原因、证据引用和旧版本 |

状态顺序建议为：`PLANNED → IMPORTING → READBACK_PENDING → VALIDATED → ACTIVE`；异常进入 `QUARANTINED`，退出监控为 `RETIRED`，不等于删除 ERP 记录。成员激活前，必须证明：本项目获准创建、实际写入已确认、独立 GET 回读、真实 ID 与关联校验、当前 G01 授权均成立。**仅名称相同、前缀匹配、POST 200 或手工粘贴一个 SKU 都不能激活。**

这里的商品身份使用 ERP 实际 product.id＋SKU 业务键，不假设存在另一个 SKU 主表接口；Listing 同时保存记录 id 和 listing_id 业务标识。无独立明细 ID 时，小试限定一张单据内同 SKU 不重复，验证稳定行定位；不能可靠定位的明细保持 UNKNOWN。

故意缺数据的负例可以是 ACTIVE 成员，但必须身份完整、异常由本项目明确设计；“成员属于我们”和“业务数据准入通过”是两个状态。旧教学批次店铺键异常，不能自动升级为 ACTIVE。当前正式清单尚未实现，按本原则正式可监控 SKU 数为 **0**。

所有入口统一使用同一 D02 公开范围解析：

- options、普通查询、单 SKU 分析、未来批量任务和前端统计，都必须先解析 `datasetId + scopeVersion`，再与当前 G01 授权求交集；不形成店×仓×SKU 的任意笛卡尔组合。
- 未登记商品默认排除；正式入口不再以“ERP 前 20 条库存”自动选监控对象。当前 `--discover-options` 只是先前工程诊断入口，**不符合新原则，后续不得用于正式启动**。
- 任务受理固定监控范围版本和成员列表；Worker 发请求前复核当前授权/停用状态。新增成员不自动扩入旧任务，撤权不能因为旧版本而失效。
- 每次新建分析仍从 ERP 按真实 ID/已登记关联读取最新事实，然后创建新的不可变快照。清单保存身份，不保存可替代 ERP 的库存和销量“答案”。
- 集合接口优先使用已验证的 IDs 或批次精确过滤、分组分页；即使 ERP 返回其他记录，也不得纳入计算。出现同名、重复、新增未登记依赖或关联漂移时，报告范围/覆盖异常，不能悄悄截断或忽略后填零。
- 前端计数和统计使用相同 scopeVersion；SKU 数按有权 ACTIVE SKU 去重，不能拿全 ERP 总数作分母。没有合法清单时显示未配置，不回退全库。
- 历史报告保留当时范围版本和快照；历史读取仍复核当前权限，不用当前数据覆盖。监控范围后续可配置、审批、版本化变更，不硬编码固定 SKU。

### 4. 可以实现的隔离程度

| 隔离层 | 能做到什么 | 不能保证什么 |
|---|---|---|
| 本项目应用层 | G01＋版本化清单严格限制查询、任务、统计和模型上下文；真实 ID/关联漂移触发隔离 | 不能阻止别人绕过本项目、直接使用 ERP 修改记录 |
| 业务数据组织 | 独立店仓、商品、Listing、供应商/单据、批次和 journal 减少误操作 | 名称前缀/tag 不是权限边界；共享店仓仍会产生竞争与归属风险 |
| ERP 权限层 | 若老师提供独立租户或专用账号、明确店仓/资源行级授权，可形成较强边界 | 目前只证明我们自己的账号权限较大，未证明其他账号被禁止访问；没有证据不得宣称硬隔离 |
| 变更检测 | 用真实 ID、关系摘要、源版本/updated_at、逐次回读和审计识别漂移 | 无源 CAS/独占权限时，读后仍可能被别人改；不能承诺跨系统原子快照 |

因此，**先向老师确认专用账号/独立范围，再激活清单**。无法提供强隔离时，须由负责人接受明确的共享风险；维持只读复核、每次采集检查和异常阻断，不能把清单说成 ERP 安全隔离。

### 5. 待批准的写入顺序与副作用边界

1. 冻结批次、精确实体/关系清单、业务预期、接口与调用上限；查重并确认独立店仓/账号范围。
2. 创建本批店铺、仓库、供应商；独立 GET，确认真实 ID/授权。若无权创建或会改变他人范围，停止相关步骤，请老师配置，不自行授权账号。
3. 创建自然命名商品、Listing 和有效报价，回读验证商品/店/仓/供应商关系；此时尚不激活监控。
4. 建立经批准的期初库存及业务订单；分别验证“仅创建”与“状态动作”的副作用。
5. **只有批准的教学工作流白名单**才执行本批采购状态动作、教学入库/出库确认等，逐项检查失败和幂等回执，再独立回读订单、未收量、库存与流水。
6. 完成历史与当前余额对账、8 类场景独立预期和来源/规则覆盖，再提交监控范围版本并激活合格成员；失败成员隔离，不整批假通过。

上述步骤是待确认方案。当前没有采购提交/下单/入库确认/出库确认的新执行授权；需要在小试批准中逐条列明。真实付款、外部发货、平台推送、通知及其他人的记录始终排除。

拟提交确认的小试接口清单为：上述主数据及单据资源的正式 POST，报价 POST，以及仅本批记录的 `/workflows/purchase-orders/{id}/submit`、`/place-order`、`/stock/inbound-orders/confirm`、必要的 `/stock/outbound-orders/confirm`。采购两个状态动作按文档不触发库存、付款或外部平台；库存确认具有真实教学库存副作用，所以必须单独列入批准范围。本次没有调用这些写路径，也不请求付款/审批接口授权。

幂等优先使用接口正式 request_key/expected_version 等能力；通用 CRUD 不假设支持 Idempotency-Key。以确定性业务键、真实 ID、请求摘要和 journal 追踪：超时先查原键/ID，确认缺失且无歧义才可受控重发；UNKNOWN 不换键重试。更新只针对本批已登记 ID，先回读核对归属和版本；没有 CAS 时需要单写者和隔离保障。不得批量清空共享数据，也不承诺已过账/已销售数据可以通用 DELETE 回滚。

### 6. 回读验收门槛

批准后逐项验收：数量达到精确批准清单；关键真实 ID/父子关系完整；销售/库存/采购/收货可有界查询且分页完整；数量、日期、状态和流水对账；8 类场景可由实际 ERP 输入触发正确计算或预期阻断；B01/B02 绑定当前快照；A01 的每条解释有事实引用；前端显示当前结果；API/Worker 重启后范围/快照/报告保持；重复导入零重复记录。

此外必须验证：未登记 SKU 排除、跨 dataset 越权拒绝、停用成员不再采集、范围变更不扩张旧任务、前端统计分母一致、他人修改或关联漂移的隔离、503/超时不变成零。对接口故障单列 FAIL/BLOCKED；对无法执行的真实正向场景记 NOT_RUN，不能用 Mock/固定 catalog 替代。
