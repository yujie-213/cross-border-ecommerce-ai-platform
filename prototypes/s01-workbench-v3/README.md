# S01 采购补货工作台 · 交互原型（v3.1）

## 打开

双击 `index.html`，用 Edge / Chrome 打开。单文件、无构建、无外部依赖、不联网。

或本地起服务（可选）：

```bash
python -m http.server 8765 --bind 127.0.0.1
# http://127.0.0.1:8765/prototypes/s01-workbench-v3/index.html
```

状态保存在内存与 `sessionStorage`（筛选），刷新重置业务数据，不写入任何系统。

## 四个入口

| 入口 | 路由 | 回答的问题 |
|---|---|---|
| 工作台 | `#/workbench` | 今天先处理什么 |
| 补货建议 | `#/suggestions` | 全部对象什么状态 |
| SKU 详情 | `#/sku/CB-1001`（Tab：`/quality`、`/history`） | 这一个补不补、补多少、凭什么 |
| 请购管理 | `#/requisitions`（单据：`/RQ-2026-0011`） | 我提交的单子到哪一步 |

## 建议审查路径（约 5 分钟）

1. **工作台**：看四个待办数字与状态分布条 → 点"待确认数量" → 应带筛选跳到列表。
2. **列表**：搜索"收纳" → 点"旅行收纳包"进入详情 → 点"← 补货建议" → 搜索词与结果仍在。
3. **详情**：结论条 20 / 55 / 75 / 4.9 天 / 11-18；下方结存曲线看负结存起始日与到货竖线；右侧改数量 25（触发整箱校验）→ 改 30 并填原因 → 勾选 → 提交；右栏立即转为"请购单 · 待 ERP 审批"。
4. **批次**：点页头"11-14 08:02 · 本次检查" → 切到 11-13 → 数值与建议数量随之变化；切回。
5. **请购管理**：双状态列（平台 / ERP）+ 进度 → 打开 RQ-2026-0012 → 步骤条第二步为琥珀色"结果待核对"，只有"原单核对"。
6. **窄窗**：拖到 1024、820 → 操作栏下移、导航转顶部、列表操作按钮不被裁切。

## 覆盖的状态

待确认（规则）｜待确认（ERP 参考，可核对后提交）｜需补证（业务日不足）｜需补证（质量调查）｜分析失败｜无需补货｜AI 解读已生成｜待 ERP 审批｜ERP 已审批｜提交待核对（UNKNOWN）｜本批次未包含。

## 自动验收（真实浏览器）

```bash
python -m http.server 8765 --bind 127.0.0.1   # 另开一个终端
node _e2e.cjs
```

`_e2e.cjs` 用 CDP 拉起 headless Edge，按真实鼠标/键盘事件走完"工作台 → 筛选 → 详情 → 改量 → 提交 → 返回 → 换批次 → 台账 → 待核对"，并在 1440 / 1024 / 820 三档宽度截图。当前 **63 项断言全部通过**，结果落在 `_e2e-result.json`，截图落在 `screenshots/after/`。

> 说明：不要用 Node 模拟 DOM 代替这一步。上一轮的"提交成功"就是用 DOM 断言 + toast 文案误判出来的假通过。

## 边界

- 数据全部为脱敏模拟值，商品、供应商、单号、日期均为构造；`演示数据` 角标与页脚是唯一环境标识。
- 不连接 ERP、不调用模型、不写任何系统。
- "15 天内 7 个有效业务日"未获批准，仅以"政策草案 · 未生效"展示，不参与判定。
- **请购管理的列表接口尚未实现**（后端只有按单据读取），本页为演示态；正式实现前须补只读列表接口，禁止前端拼装历史冒充台账。
