# S01 UX v3.2：可视化选型、AI 分区与遗留问题修复

- 分支：`review/workbuddy-s01-ux` · 日期：2026-11-14 · 状态：**REVIEW**
- 范围：只改原型、测试、设计文档与截图；未改 `frontend/`、`src/`、`migrations/`、`tests/`
- 原型：`prototypes/s01-workbench-v3/index.html`（顶部 A / B / C 可切布局，URL 亦可 `?v=a|b|c`）
- 验收：CDP 驱动真实 Edge，三档宽度，**76 项断言全部通过**

## 0. 一句话

上一版把"文字墙"换成了"条形图墙"。这版逐个组件问了一遍"这块到底要让用户比较什么"，删掉了 4 处横向条形、1 处重复分布图，把 AI 从右下角小卡提为**结论条正下方的独立分区**，并用真实浏览器把三个遗留缺陷钉死。

## 1. 逐组件可视化选型

判断依据：**该区域要用户做的事**（比数量 / 看占比 / 看趋势 / 判风险 / 跟流程），而不是"有没有图"。分母不可靠、类别过多、或与其他区域重复的，一律不画。

| # | 区域 | 要传达的信息 | 候选形式 | 最终 | 依据 |
|---|---|---|---|---|---|
| 1 | 工作台·对象构成 | 12 个对象里多少要处理、多少已了结 | 7 段堆叠条 / 7 段环形 / 4 组环形 / 纯数字 | **4 组环形（104px）** | 7 段在 104px 下每段 30° 不可辨，且 5 个"1 项"互相无法区分。按**处置动作**归 4 组（待人工处理 8 / 已提交待批 2 / 无需补货 1 / 分析失败 1），环形负责"形状"，明细在 KPI 与图例 `title` |
| 2 | 工作台·建议来源 | 规则 / ERP 参考 / 无来源 的占比 | 环形 / 堆叠条 / 数字+百分比 | **数字 + 百分比 + 色点** | 只有 3 类，占比用数字直读比任何图形都快；且环形已被 #1 占用，同页两个环形属重复表达 |
| 3 | 工作台·覆盖最短 | 谁的库存最先见底 | 横向条形排行 / 带天数与交期的排行 | **排行（覆盖天数 / 交期天数）** | 条形只能表达"相对长短"，而这里要比的是**两个真实数值的差**（覆盖 4.9 天 vs 交期 12 天）；数字直读 + 短于交期标红，比条形精确 |
| 4 | 列表·库存列 | 该 SKU 库存够不够 | 行内条形 / 数字+覆盖天数 | **`55 / 75` + `覆盖 4.9 天` + 风险标签** | 待补货对象的填充率**必然 <100%**，条形不提供额外信息；覆盖天数才是可比、可决策的量。同时消除与 #3 的同形重复 |
| 5 | 详情·结存与缺货 | 什么时候断、断多少 | 折线 / 面积 / 柱状 | **折线 + 负结存区着色 + 到货竖线** | 时间序列 + 阈值（0 轴）+ 事件（到货），三者叠加只有折线能做到；柱状会让"连续结存"变成离散错觉 |
| 6 | 详情·每日销量 | 需求是否平稳、有无脉冲 | 柱状 / 折线 / 迷你火花线 | **柱状（7 日）+ 日均虚线** | 逐日比较用柱；日均线给基准。日均未知时**不画**均线（见 §4） |
| 7 | 详情·库存覆盖天数 | 够不够撑到到货 | 环形仪表 / 刻度尺 / 纯数字 | **纯数字 + "低于交期（交期 12 天）"** | 决策输入就是"4.9 vs 12"两个数；仪表盘只增加装饰，不增加精度 |
| 8 | 详情·已有采购 | 采购/已收/待收 的构成 | 堆叠条 / 三段数字 | **三段数字 + 比例条（仅在有单据时）** | 60=24+36 是可靠分母的组成关系，堆叠条合适；无单据时不渲染空条（v3.1 曾画过 0% 空条，已删除） |
| 9 | 请购·单据进度 | 单据走到哪一步 | 三点进度 / 步骤条 / 百分比 | **列表三点段 + 详情四步条** | 列表要扫，三点段够；详情要解释"下一步谁负责"，四步条 + 未完成态文案 |
| 10 | 请购·状态分布 | 三种状态各几单 | 环形 / 堆叠条 | **删除** | 分段控件的按钮上已有计数（全部 5 / 待审批 3 / 已审批 1 / 待核对 1），再画一遍属装饰。删除后页面只剩"筛选 + 台账" |
| 11 | 详情·依据与限制 | 哪些事实不可信 | — | **文字清单（不画图）** | 责任人、下一步、影响范围是文本信息，图形化只会丢信息 |
| 12 | 详情·建议口径 | 20 件是怎么来的 | — | **算式 `75−55−0=20`** | 数量推导用算式最清楚，且能一眼校验与建议值是否自洽（这是 v3.1 的真实缺陷来源） |

**共删除**：工作台堆叠分布条、队列库存条、来源迷你条、覆盖排行条（4 处横向条形）+ 请购页分布条（1 处重复图表）。当前全站图形：环形 ×1、折线 ×1、柱状 ×1、堆叠条 ×1（仅在途）、进度段 ×2。同一页面不再出现两种同形条形图。

## 2. AI 分区设计

### 2.1 角色边界（写进界面，不只写在文档）

| 角色 | 负责 | 界面上怎么体现 |
|---|---|---|
| ERP | 提供事实（库存、销量、报价、采购单） | 数据时点、来源、依据页的字段值 |
| 规则引擎 | 计算建议数量与缺货风险 | 结论条第 1 格固定叫**「规则建议」**；算式区展示推导 |
| AI | 解释事实、提示风险、列出待核实项 | AI 区独立成块，头部固定"基于规则结果与已读取事实"，页脚固定"仅解读，不改动规则建议数量" |

AI 区不出现数量输入、不出现"建议采购 X 件"的措辞，避免与规则建议混淆。

### 2.2 内容结构（按决策顺序，不是聊天顺序）

```
[AI] 智能分析  [已生成]  基于规则结果与已读取事实
结论一句话（覆盖 X 天 → 到货在缺口之后 → 存在断货窗口）
关键事实(3)          风险与不确定(2)        建议人工核实(2)
来源 本次单品分析 · 时点 · Token · 费用                    仅解读，不改动规则建议数量
```

四段固定：**结论 / 关键事实 / 风险与不确定 / 建议人工核实**。详细解释不再往下堆——每条已是可核对的短句。

### 2.3 状态机

| 状态 | 触发 | 界面 |
|---|---|---|
| 未生成 | 该 SKU 尚无解读 | 一个次级按钮"生成 AI 解读" + 一句范围说明（不抢视觉） |
| 生成中 | 点击后 1.2s | 三行骨架 + "正在基于本次已读取事实生成解读…" |
| 已生成 | 成功 | 四段结构 + 元信息 |
| 生成失败 | 超时/异常 | 红色一行说明 + 「重试」+ "规则结论与建议数量不受影响" |
| 无可用事实 | 数据不足/质量阻断 | 一句原因 + 「查看缺失项」跳依据页 |

不提供多轮对话、不提供"自动执行/提交"，也不编造模型发现的风险——所有条目都引用已展示的事实。

### 2.4 三种布局与选择

| 方案 | 结构 | 优点 | 问题 | 截图 |
|---|---|---|---|---|
| **A** | 图表 → AI（全宽）→ 分区；操作在右侧固定栏 | AI 有全宽排版，操作随时可见 | AI 被图表压到 800px 以下；右侧 336px 在操作卡之下大片空白 | `screenshots/after/05-布局A-AI全宽分区-1440.png` |
| **B** | 图表 → 分区；AI 与操作同处右栏（AI 在上） | 分析与操作同屏，滚动少 | 320px 栏内四段结构退化为竖排长文（本轮实测 3 列被压成窄条，已修但依然难读）；操作被推到 AI 之下 | `screenshots/after/06-布局B-AI右栏-1440.png` |
| **C（推荐）** | 结论条 → **AI（全宽，紧跟结论）** → 图表 → 分区；**底部常驻操作条** | AI 首屏可见且是主要分区；图表获得全宽（原 760→1156）；操作与 AI 互不挤占，随时可提交 | 需要底部条承担"当前数量/校验/提交"，移动端需压缩 | `screenshots/after/07-布局C-AI前置-1440.png` |

**推荐 C**，理由按重要性排序：

1. **AI 的存在感来自位置与宽度，不是字号**。C 把它放在用户读完结论后的第一落点，且给足横向空间做三栏对照；B 里它只能竖排长文，A 里它被图表压到折叠线附近。
2. **操作不该和 AI 抢同一列**。B 把两者塞进 320px，先看 AI 就够不到按钮，先按按钮就得跳过 AI。C 用底部条把"随时可提交"与"AI 阅读"解耦。
3. **图表值得全宽**。去掉右栏后折线图从 ~760px 增至 ~1156px，9 个业务日不再挤在一起。
4. 代价可控：底部条高度 51px，内容区加 `padding` 后不会永久遮挡；≤1000px 隐藏次要文案，主按钮仍在首行（已断言）。

顶部 A/B/C 开关仅用于评审对比（原型专用），正式实现只保留 C。

## 3. 三项遗留问题

### P1-A 待核对单据排序

- **缺陷**：`rank=s=>({req_unknown:0,...})[stageOf(s)]||9` —— 优先级 `0` 是合法值，`||` 把它当成假值替换为 9，最紧急的"待核对"反被排到最后并被 6 条上限截掉。
- **修复**：改为显式查表 + `undefined` 判断：

```js
const RANK={req_unknown:0,missing:0,failed:1,blocked:2,confirm:3};
const rank=s=>{const v=RANK[stageOf(s)];return v===undefined?9:v;};
```

- **回归**：断言"待处理队列首行必须是 CB-1030（提交待核对）"，`76/76` 中通过。

### P1-B 零库存覆盖天数

- **缺陷**：`if(!p.available||!p.avgDaily)return null` —— 库存 `0` 为假值，被当成"未读取"，于是缺货对象显示"—"。
- **修复**：区分四种输入：

| 输入 | 结果 | 界面 |
|---|---|---|
| `available=0` | `0` | "0 天" + 低于交期（红） |
| `available=null` | `null` | "—" |
| `avgDaily=0` 且 `available>0` | `Infinity` | "无需求" |
| `avgDaily=null` | `null` | "—" |

- 交期未知（`lead` 为空）时**不判定风险**，避免用颜色冒充结论。
- **回归**：新增零库存对象 CB-1040（可用 0、日均 5.2、交期 12）。断言工作台行、排行卡、列表行均显示 `0 天` 而非 `—`。

### P1-C ERP 参考建议提交链路

- **缺陷**：没有覆盖"ERP 来源也能人工确认提交"的端到端验证，容易被后续改动悄悄退回"一律禁止"。
- **保留方案 B**：来源算法未核实 ≠ 不可采购；核对 MOQ / 整箱 / 报价有效期后可提交。
- **回归**（真实浏览器逐步执行）：

```
打开 LT-3012（ERP 参考）→ 断言状态=待确认、来源标"ERP 参考"
→ AI 区存在且引用 ERP 建议记录
→ 切「依据与限制」断言"ERP 计算依据未核实"可见
→ 切「采购条件」断言最小起订量可见
→ 勾选"已核对采购条件与在途" → 断言提交按钮启用
→ 提交 → 断言状态=待 ERP 审批、生成新单号 RQ-2026-0014
→ 台账出现该单（5 行）
```

## 6. 剩余限制

1. **请购列表接口仍不存在**。`s01_v2.py` 只提供按单据读取（`/singles/{task_id}/requisition`），台账为演示态。
2. **原型在本地推算结存与首次短缺**，仅为让演示自洽；正式实现必须消费后端 B01 结果，禁止前端复刻（见 §7）。
3. 演示数据 12 个对象、3 个批次；不足以验证分页、大批量性能与图层密集场景。
4. 底部操作条在 <680px 且填写"调整原因"时会占两行（已隐藏次要文案，未做进一步移动端优化）。
5. 未做：批量确认、导出、审批动作、多轮 AI 对话（均无后端与授权前提）。

## 7. 正式 Vue 改造的数据契约与接口依赖

> 原则：**数量、结存、短缺日一律来自后端**；前端只做展示与格式化。

| 界面元素 | 需要的字段/接口 | 现状 | 缺口 |
|---|---|---|---|
| 工作台环形（4 组） | 按阶段的计数（或全量 items 分组） | `GET /s01/v2/batches/{id}/items` 已知，但需全量拉取 | 建议后端提供 `summary.countsByStage`，避免前端拉全量再汇总 |
| 建议来源占比 | `sourceGrade` | 已有 | — |
| 覆盖天数 | `available`、`avgDaily`、**`leadDays`** | `inventory.available`、`ruleResult.forecast.averageDailyDemand` 有；**交期未在 v2 item 契约中** | 需补 `constraints.leadDays`（来自有效报价交期），否则无法判定"低于交期" |
| 首次短缺日 | 后端计算结果 | 原型自算 | 需后端返回 `firstShortageDate`（B01 序列口径），前端不得重算 |
| 结存曲线 | `projectedDaily[{day,demand,arrival,closing}]` | **无** | 需 B02/B01 输出未来 9 日投影；现有 `forecast.dailySales` 只有历史 |
| 每日销量柱 | 已核对业务日销量 | 部分（`dailySales`） | 需明确"完整业务日"过滤与窗口字段 |
| 在途构成 | `formalPurchases[].ordered/received/unreceived/plannedArrival/sellableDate` | 已有 | 保持"无承诺可售日不计入有效在途"的语义 |
| AI 四段 | `analysisReport.ai.status` + `explanation{conclusion,facts,risks,checks}` + `usage` + `generatedAt` | 现有 `explanation` 为四类文本数组（recommendationReasons/keyEvidence/majorRisks/humanConfirmations） | 需与后端对齐字段名；前端按"结论/事实/风险/待核实"映射，**不得新增模型调用** |
| AI 五态 | `NOT_ATTEMPTED / RUNNING / AVAILABLE / FAILED / NO_FACTS` | 现有 `AVAILABLE / NOT_ATTEMPTED / UNAVAILABLE` | 需补 `RUNNING` 与"无可用事实"的独立状态码，便于区分"没跑"和"跑不了" |
| 请购台账 | `GET /s01/v2/requisitions` | **无** | P0 阻塞项；禁止前端拼装 `/singles` 历史冒充 |
| 请购双状态 | `platformStatus`、`erpStatus`、`verifiedAt`、`readbacks` | 现有 requisition 对象含 `state/erpStatus/verifiedAt` | 需明确"平台已提交·未确认"与"ERP 未知"是两个字段 |
| 提交幂等 | `Idempotency-Key` + 原单核对 | 已有契约 | 前端"原单核对"只读，不得重发 |

**实现顺序建议**：接口字段对齐（本节）→ P0 台账接口 → 路由外壳 → 列表/详情拆分 → AI 分区 → 收口。在字段补齐前，Vue 版不要把原型里的本地推算搬过去。
