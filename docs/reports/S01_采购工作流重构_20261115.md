# 采购工作流重构 · REVIEW 工作记录

起点：`codex/alienware-local-deployment` / `474cc6957c803a1893ad49a7018963e090f73448`，工作区干净。用户已授权产品级前端重构、必要交互修复、真实浏览器和必要模型验证；不合 main，不做 ERP 写入。

## 设计先于组件

采购专员的任务是发现风险、按仓做判断、理解 AI 建议并决定行动。采购主管需要快速了解风险与进度。

- 平台层：首页只提供已实现 Agent 入口、近期真实任务和异常；进入智能补货后才出现工作区导航。
- 工作区：以优先处理队列为主，少量业务数字辅助；检查进度和失败操作就地反馈。
- 商品列表：按商品归并，显示需补仓数、库存/需求必要摘要、风险日期；每行有明确“分析商品”操作，筛选保留在 URL。
- 商品详情：商品头与固定分析入口 → 分仓结论 → AI 行动建议 → 销量/库存证据及 ERP 差异 → 右侧人工采购决策。分析入口只取决于身份/任务状态，不取决于采购资格。
- 图表只解释已存在的后端事实：销量柱展示有记录日；库存折线标零线及首次短缺；ERP 用并列数值和差异条。无数据保留原因，不补零、不造预测。
- AI 展示一条核心建议、少量行动和风险，完整证据折叠。刷新分析和请求 AI 是两个明确动作，均立即显示受理状态；失败有重试。结果绑定 SKU、店仓与具体分析，切换清除旧状态。
- 采购侧栏清楚区分参考补充与满足约束的采购候选；未满足采购条件仍能分析。已有单据、未确认操作、幂等和 CSRF 校验继续生效。

## 需验证的根因

旧详情包含多个完整报告组件，导致重复与长页面；底部分析按钮置于采购资格分支之后；AI请求在返回前保留旧结果、失败态缺少生成按钮；共享详情状态在创建请求返回及切换对象时存在竞态；只读请购状态仍被前端提交资格门控。

## 验收

以本机现有10款/11店仓为范围。真实浏览器覆盖首页、工作区、筛选、双仓、增长品、无报价品、实际AI点击/返回、失败反馈、返回刷新切换；截图和实际结果在完成后补录。模型只用本机配置，显式用户请求范围；采购提交保持关闭，不改算法/迁移/登记数据。

## 缺陷根因与修复

| 原问题 | 本轮结果 |
|---|---|
| 分析入口位于采购资格条件分支后，结果不同导致按钮消失 | 商品头固定更新分析入口，AI入口包含未生成/成功/失败，提交资格单独控制采购表单 |
| AI请求返回前旧报告仍可见；失败态没有按钮 | 点击即清旧解读并显示受理/运行态；成功原位展示，失败显示原因和重试 |
| 创建请求、轮询及切换店仓并发时共享状态可能串页 | 详情代次及对象/检查上下文校验，异步旧响应不覆盖新对象；单品报告必须匹配当前店仓 |
| 快速搜索后进入详情，被未取消的延迟搜索抢回列表 | 页面卸载取消延迟回调，初始化及筛选更新期间禁止误点旧结果 |
| 请购只读状态依赖提交资格，且只读本地历史 | 查询与写权限分开，新增有限范围的实时ERP只读状态，原提交门保持 |
| 任务截止时间显示为“上次检查时间” | 新增实际createdAt投影并使用业务数据时点，未知时间不编造 |

- 用户随后明确授权开启本机采购提交，现已生效。真实浏览器验证条件满足并人工勾选后按钮可用，改量原因/MOQ整箱/缺报价等约束仍强制；没有实际提交采购、审批或下单。
- 状态以打开/刷新及60秒轮询更新，有限范围按ID回读；不是ERP全量单据搜索或推送订阅。
- 真实AI验证授权为独立4次/96000 Token/0.20 USD预约上限，自动验收使用2次；当前策略累计3次7162Token、$0.15风险预约/实际费用UNKNOWN，尚余1次；额度不足会明确提示，不静默切换模拟模型。
