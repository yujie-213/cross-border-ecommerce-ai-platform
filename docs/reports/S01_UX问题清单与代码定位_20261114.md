# S01 V2 前端体验问题清单与代码定位

- 分支：`review/workbuddy-s01-ux`（基点 `ece1116`，与 `codex/s01-data-admission-review` 工作目录隔离）
- 日期：2026-11-14
- 范围：只审查与记录，未修改任何正式业务代码、数据库、API 与测试基线
- 结论等级：**REVIEW 材料**，不改动 `docs/TASKS.md` 任务状态，不代表任何验收

## 0. 一句话结论

现有 V2 工作台的**信息本身是充分的，问题在于它被组织成一个单一长页面**：路由只换标题、左侧导航不换内容，SKU 详情没有独立空间，请购与审批概念混在一个面板里。这四件事叠加，使采购运营人员无法按"先扫、再判、再办"的节奏工作。

## 1. 审查方法

1. 静态阅读 `frontend/src/**`（`App.vue` 85 行、`V2Workbench.vue` 163 行等，共 16 个源文件）。
2. 对照 `docs/ui/PRODUCT_SPEC.md`（四页面规格）、`docs/DESIGN.md`（视觉规范）、`docs/contracts/s01/p3-minimal-loop.md`（请购契约）。
3. 核对后端实际路由 `src/commerce_hub/entrypoints/http/s01_v2.py`，确认前端可消费的数据边界。
4. 核对现有浏览器测试 `tests/browser/s01/*.spec.ts`，确认问题为何未被测试拦住。
5. 用新的可交互原型验证替代方案（见 `prototypes/s01-workbench-v3/`）。

## 2. 问题清单

### P1【严重】左侧导航与主体内容不联动

**证据**

| 位置 | 代码 | 说明 |
|---|---|---|
| `frontend/src/App.vue:59` | `<V2Workbench v-if="v2Enabled && connected" @denied="w.connect()" />` | 该行位于所有 `route` 判断**之前**，且不带 `route` 条件 |
| `App.vue:60` | `v-else-if="route === 'workbench' \|\| route === 'suggestions'"` | V2 开启后此分支永不执行 |
| `App.vue:80` | `<template v-else>` 人工审批分支 | 同理永不执行 |
| `App.vue:19-22` | `routes` 映射 + `location.hash` | 路由只驱动面包屑文本与 `nav a.active` 高亮 |
| `App.vue:53` | `:class="{ active: ... key === 'suggestions' && route === 'detail' }"` | "分析详情"被折叠进"补货建议"高亮，进一步掩盖了没有详情页的事实 |

**用户可见后果**：点"补货建议""人工审批"，标题变了、导航高亮了、**内容一个像素都没变**。URL 无法分享、无法刷新恢复、浏览器后退只会改标题。

**判定**：这是四页划分失效的根因，其余问题都由它派生。

---

### P2【严重】所有功能堆叠在单一长页面

**证据**：`frontend/src/components/V2Workbench.vue:117` 是一个 `display:grid` 的单列容器，其直接子节点按顺序为：

| 行 | 内容 | 问题 |
|---|---|---|
| 118-122 | 页头 + hero 宣传块 | 每次进入都占 ~120px，重复陈述"来源透明" |
| 123-133 | 本次批量检查（含 8 个指标、任务 ID、4 条 Notice） | 与列表无视觉分层 |
| 134-140 | 结果表格（7 列 + 6 个筛选器） | 页面主体 |
| 141-155 | **SKU 详情**（内嵌 6 个子面板 + 原始 JSON） | 打开详情后在表格**下方**追加，需要滚动穿越整张表 |
| 156 | 批量任务历史 | 又一张表 |
| 157 | 单品分析历史 | 再一张表 |

**用户可见后果**：页面长度随数据线性增长；打开 SKU 时视野不移动（`openItem` 只赋值 `selected`，无滚动/抽屉/路由），用户以为自己"点了没反应"，需要手动向下找。

---

### P3【严重】SKU 详情缺少独立操作空间

**证据**

- `V2Workbench.vue:56` `openItem()` 仅设置 `selected.value`，不改变 URL、不打开抽屉、不滚动。
- `V2Workbench.vue:141` 详情面板标题是 `current.name + ' · ' + current.sku`，无独立页头、无返回路径。
- 详情的 6 个子面板（`146` 采购条件、`147` 仍需核实、`148` 规则计算、`149` AI、`150-152` 请购、`154` 证据 JSON）全部展开，无法折叠。
- `App.vue:74` 的"返回补货建议"链接硬编码 `#suggestions`，而详情从未是一条路由，返回语义无处落地。

**后果**：无法"打开一个 SKU 专心判断"，也无法把某个 SKU 的判断链接发给同事。

---

### P4【严重】"人工请购"与"审批"概念混淆

**证据**

| 位置 | 内容 | 问题 |
|---|---|---|
| `App.vue:19` | `approvals: '人工审批'` | 导航名 |
| `App.vue:53` | 导航第三项 `approvals: '人工审批'` | 平台**没有**审批能力 |
| `App.vue:80` | `<h1>人工审批</h1>` + `<p>复核当前报告，确认销售备货数量后提交 ERP 请购。</p>` | 标题说审批，副标题说提交 |
| `V2Workbench.vue:150` | 面板名"人工确认与 ERP 请购"，备注"只创建并提交申请，待 ERP 领导审批" | 这里才是正确表述 |
| `V2Workbench.vue:152` | 勾选项"…不将此确认视为 ERP 领导审批" | 需要用户自己读长句才知道区别 |

`docs/contracts/s01/p3-minimal-loop.md` 明确规定：**"页面明确'待ERP审批'，中台人工确认不代替ERP领导决定"**。当前导航用词与契约相反。

**后果**：运营以为点完就"批了"，实际只是提交；而 ERP 侧待审批的单据在平台里没有任何入口可看。

---

### P5【高】请购表单存在两套并行实现

**证据**

| 实现 | 位置 | 校验 | 确认语义 |
|---|---|---|---|
| V1 | `components/RequisitionPanel.vue:86-97` | 自建校验 `:17-22`，无 `sourceAcknowledged` | 边勾选边提交 |
| V2 | `components/V2Workbench.vue:150-152` | `api/v2.ts:23-28` `quantityError()`，需 `sourceAcknowledged: true` | 同左 |
| 校验副本 | `api/v2.ts:23-28` | 与 `RequisitionPanel.vue:17-22` 规则文字不同 | 两处维护 |

`App.vue:77` 与 `App.vue:80` 各自渲染一次 `RequisitionPanel`。

**后果**：同一业务动作有两种交互与两套提示文案；改 MOQ/整箱规则需要改两个文件，容易漏改。V2 路径已带 `sourceAcknowledged`，V1 路径不带，若后端收紧校验，V1 表单会静默失败。

---

### P6【高】重复警告与信息噪声

**证据**（同一 SKU 的"数据不足"会被说 3 遍）

- `V2Workbench.vue:143` `Notice` ERP 参考建议
- `V2Workbench.vue:144` `Notice` 未形成正数量
- `V2Workbench.vue:145` 归属问题 + `ruleFailureCodes` 两段文本
- `V2Workbench.vue:147` `Notice` "仍需核实的事项"（`uncertainties` 再列一次）
- `V2Workbench.vue:130` 又在批量层提示 `sourceLimits` 不完整

**后果**：真正重要的那一条阻断被淹没；用户形成"这些黄条不用看"的习惯，这比不提示更危险。

---

### P7【中】技术标识直接暴露在业务视野

**证据**：`V2Workbench.vue:124` 任务 ID 以 `mono` 全角展示；`154` 把 `snapshotRef`、`inventory`、`sourceSuggestion` 等 8 个字段 `JSON.stringify` 后 `<pre>` 直接铺在页面；`HistoryTable`（`components/HistoryTable.vue`）首列是截断 12 位的 `taskId`。

**后果**：采购人员需要的是"哪个 SKU、差多少、什么时候断"，而不是 UUID。长 ID 还挤占了表格宽度。

---

### P8【中】筛选与历史不进入可恢复状态

**证据**

- `V2Workbench.vue:16` 7 个筛选 ref 只在组件内存中；`102-103` 变化即重查，无 URL 参数。
- `V2Workbench.vue:111` `sessionStorage` 只存 `batchId`/`singleId`，不含筛选、不含当前 SKU 详情、不含当前分区。
- `App.vue:29` `watch(filteredChoices)` 在筛选变化时**清空选中项**。

**后果**：刷新丢筛选；从详情返回无法回到原筛选位置；分享链接只能分享到"工作台"。

---

### P9【中】指标口径与页面密度

**证据**：`V2Workbench.vue:127` 把 8 个指标塞进 `v2-metrics`（`161` 定义 4 列）→ 两行各 4 个，其中"发现 SKU"（商品维度）与"店仓分析对象"（对象维度）并排且量级不同；`V2Workbench.vue:161` `@media(max-width:640px)` 才降到 2 列，1440 下仍挤。

**后果**：两组不同分母的数字被读成同一序列，容易得出"覆盖率高但失败多"的错误判断。

---

### P10【低】无障碍与语义

- `App.vue:53` 导航图标用 `▦ ≡ ☑` 字符，未 `aria-hidden`，屏幕阅读器会读成符号。
- `V2Workbench.vue:137` 表格无 `<caption>`，`<th>` 无 `scope`。
- `V2Workbench.vue:117` 整页无 `role`/`aria-label` 分区，跳转链接 `#main` 只在 `App.vue:52` 提供。

## 3. 测试为何没拦住

| 现象 | 证据 | 说明 |
|---|---|---|
| 导航不联动无人发现 | `tests/browser/s01/v2.spec.ts:19`、`:56`、`local-platform.spec.ts:22/38/53/65/80/93` 均只断言 `heading '全量补货工作台'` | 因为该 H1 在任何路由下都存在，断言恒真 |
| 点击导航后仍操作同一张表 | `tests/browser/s01/workspace.spec.ts:52`、`:92`、`:115`、`:193` 点击"补货建议"后直接操作表格 | 测试**以 Bug 为前提**编写，反而固化了它 |
| 详情无路由 | `v2.spec.ts:21` 用 `getByRole('row')…'查看详情'` 后断言 `heading /HL-CBL100-2M/` | 断言的是页内出现标题，不校验 URL/可返回性 |

**结论**：本次改造必须同步补一条"导航切换后主体内容变化且 URL 变化"的断言，否则同样的问题会再次回归。

## 4. 后端能力差距（影响方案可行性，非前端可解）

| 需求 | 现状 | 证据 | 影响 |
|---|---|---|---|
| 请购单跨 SKU 列表 | **无接口**。只有 `GET /s01/v2/singles/{task_id}/requisition` 单任务读取 | `src/commerce_hub/entrypoints/http/s01_v2.py:122-127` | "请购管理"页目前无法用真实数据渲染列表 |
| 单品历史带请购摘要 | `GET /s01/v2/singles` 只回填 `sku/entityKey/sourceGrade` | 同文件 `106-114` | 无法在列表里显示"该 SKU 是否已请购" |
| 批次内单 SKU 重算 | 只有 `POST /batches` 全量、`POST /singles` 单品 | 同文件 `51`、`90` | "重新分析此 SKU"只能走单任务，成本与语义需确认 |

**处理方式**：原型中"请购管理"为**演示态**并在界面与文档中注明；正式前端该页必须等接口补齐，禁止用前端拼装 `singles` 历史冒充请购台账。
