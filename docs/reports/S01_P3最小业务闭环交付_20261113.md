## 4. 权限、校验与恢复行为

| 入口 | 所需条件 | 行为 |
|---|---|---|
| 分析/读取报告 | 原 G01 tasks:create/read + ACTIVE范围 | 既有分析及不可变报告；正式采购来源失败明确阻断/限制，不用 Mock 替代 |
| `POST /api/v1/analysis-tasks/{id}/requisition` | tasks:read、独立 `s01:requisition`、可信 Cookie/Bearer、Cookie变更CSRF/Origin、原报告/当前ACTIVE映射、Idempotency-Key | 仅整数最终量与原因，拒绝客户端租户/价格/供应商/状态等额外字段；新旧快照/候选/约束与正式采购信息重算核对，变化须重分析；新申请报告不得超过24小时 |
| 同路径 GET | 当前 tasks:read、同租户/范围成功报告 | 只读已保存操作与最后独立 ERP 核验时间，不后台审批或创建；后续ERP状态变化不伪装实时刷新 |
| ERP create/submit | 显式教学启用开关 + 已授权内部资源 + 当前写权限 | 只有创建采购申请和submit两种窄写动作；每次网络前重新核权，无数据库锁跨网络 |

一个源报告只有一个操作，数据库唯一约束和阶段领取防止并发双击；不同 key、同内容也返回原记录，不同内容冲突。保存 AI 原数量、人工最终量、原因、源快照、重新核验摘要、范围/批次、实际主体、ERP ID/单号和状态，不覆盖原分析。

创建发送前持久化原业务号与发送阶段。发送超时/崩溃后按原业务号核验；找不到仍 CREATE_UNKNOWN，**不自动重建**。submit未知先查原 ID；确认仍草稿时仅沿原 ID 重试契约幂等 submit。已知 HTTP 拒绝与 UNKNOWN 分开反馈。单据不符/多条或报告变更会 BLOCKED；先处理遗留单再重分析，不得把新分析当成清理旧未知结果的方法。

浏览器超时保留原 key/数量/原因；刷新或人工审批页面可读取已保存结果，未结束操作可用原操作继续核对。关闭/刷新页面不撤销已发给 ERP 的业务请求；不会把中台确认称为 ERP 领导批准。
