# S01 采购补货工作台 · UX v3 交互原型

## 打开方式

**方式一（推荐，双击即开）**：直接双击 `index.html`，用 Edge / Chrome 打开。单文件、无构建、无外部依赖、无远程资源、不联网。

**方式二（本地静态服务）**：从项目根目录运行

```bash
python -m http.server 8765 --bind 127.0.0.1
```

然后访问 <http://127.0.0.1:8765/prototypes/s01-workbench-v3/index.html>。这只是本地预览，不是部署。

原型状态全部在页面内存与 `sessionStorage` 中，刷新会重置业务状态、保留筛选；不会写入任何系统。

## 这个原型要证明什么

现有 V2 工作台把所有内容堆在一个长页面里，左侧导航点了不换内容。这个原型用**四个业务入口 + 真实路由**重做一遍，验证"扫 → 判 → 办"的节奏是否成立：

| 入口 | 地址 | 回答的问题 |
|---|---|---|
| 工作台 | `#/workbench` | 今天我要处理什么 |
| 补货建议 | `#/suggestions` | 全部对象现在什么状态 |
| SKU 详情 | `#/sku/CB-1001` | 这一个该不该补、补多少、凭什么 |
| 请购管理 | `#/requisitions` | 我提交的单子到哪一步了 |

## 建议审查路径（约 6 分钟）

1. **工作台**：看四张待办卡（3/3/3/1）→ 点"待人工确认"→ 应带着筛选跳到列表。
2. **列表**：搜索"收纳"、切店铺 → 点任一 SKU 名称进入详情 → 点"← 返回补货建议" → **筛选还在**。
3. **详情（CB-1001）**：结论条 20/55/90/11-18 → 切到「销售与库存」看逐日结存与负结存 → 切「依据与限制」看数据来源与"查看依据"弹窗。
4. **数量校验**：右栏把数量改成 25 → 提示"必须是整箱倍数"且按钮禁用；改成 30 → 要求填原因；勾选确认 → 提交 → 状态变为"已提交 · 待 ERP 审批"。
5. **数据不足（LT-3021）**：建议数量显示"— / 未形成"，右栏明确"暂不可提交请购"，政策草案标注"未生效"。
6. **请购管理**：看三种状态（待审批 / 已审批 / 待核对）→ 打开 RQ-2026-0012 → 只提供"使用原单核对"，提示不要新建第二张申请。
7. **窄窗**：把窗口拖到 1024、900、820，确认操作栏下移、导航转顶部、表格不被裁切。

完整逐条验收见 `docs/reports/S01_UX_V3_改造路线与验收清单_20261114.md` §3。

## 自动校验

```bash
node _verify.cjs
```

覆盖：数据结构、9 个页面渲染（无 `undefined` 泄漏）、关键文案、数量校验规则、筛选逻辑、以及**完整提交链路**（改量无原因被拒 → 填原因可提交 → 状态与计数同步变化）。当前 74 项全部通过。

`node --check` 之外没有构建步骤；如果修改了 `index.html` 里的脚本，建议重跑一次。

## 边界声明（重要）

- 全部为**脱敏模拟数据**，商品名、供应商、单号、日期均为构造值。
- **不连接 ERP**、不调用任何模型、不读取本机密钥或 `.env`。
- 原型**不代表**任何真实业务结论；四项企业门仍为 BLOCKED。
- "15 天内 7 个有效业务日"未确认，为此原型只把它作为**政策草案（未生效）**展示，不参与任何数量判定。
- "请购管理"页的列表在真实系统中**尚无对应接口**（只有按单据读取），原型为演示态；正式实现前必须先补只读列表接口，详见改造路线 P0。
- 本原型不修改任何正式业务代码、数据库、API 或测试基线。
