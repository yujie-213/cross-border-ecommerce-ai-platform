跨境电商智慧中台 AI 应用项目需求文档草案

文档编号：AIH-PRD-DRAFT-001 ｜ 版本：0.2 ｜ 日期：2026-11-11 ｜ 状态：R01—R09 修订稿，待独立复核

核心设计：面向 S01—S10 完整业务规划，分阶段实施；O01 负责统一任务编排，场景负责领域业务步骤与判断，通用能力负责可复用实现；指标、事实、证据、审批和执行分别只有一个权威归属。

01 文档目的与依据

本草案用于项目立项、范围评审和研发拆分，明确业务目标、逻辑架构、模块职责、扩展契约、首期功能和验收原则。它是建议方案，不代表企业系统已接通、需求已批准或生产能力已验证。

业务依据为《跨境电商业务流程与术语指南》第 01—03、07—17、19—20 节，以及本次讨论形成的 22 项候选场景。原指南链接的其他需求、接口和验收文档未在当前工作区提供，因此本草案不复用其 HUB、API、UAT 编号，也不声称已核对这些文档。

本草案中的 P0/P1/P2 表示拟议建设阶段。阈值、供应商、模型、预算和上线规模需在评审后冻结；未经批准的拓展场景不自动进入首期范围。

02 业务目标、用户与成功标准

2.1 目标

  1. 让运营、采购、仓库、客服和财务基于同一对象、同一时间窗口和明确口径讨论问题。
  2. 支持补货、履约、客户之声（VOC）和经营贡献的联合分析，给出事实、候选原因、方案和不确定性。
  3. 将可执行建议交由业务人员确认和审批，经受控执行器回到原系统创建有限动作，并追踪业务结果。
  4. 建立可复用能力，新增场景通过组合服务和注册策略实现，避免重新开发取数、计算、检索及审批。

2.2 用户与责任

角色 核心诉求 项目内责任
运营、采购 缺货何时发生、补多少、有哪些备选方案 确认业务范围、假设和建议参数
仓库、物流负责人 哪些异常影响订单、哪个节点需核实 核实库存、质检和履约事实，在原系统办理业务
客服、商品负责人 客户反复反馈什么、是否需调查 复核主题和证据，跟踪内部调查
财务 贡献变化是否真实、缺哪些费用 确认费用、币种、成本及核算口径
经理、授权审批人 方案依据、风险及资源影响 独立审批具体动作及其有效期
集成、数据及运维人员 来源是否完整、任务能否恢复 维护映射、数据质量、连接器和运行状态
审计人员 结论和动作如何形成 按权限回溯输入、版本、审批和回执

2.3 成功标准

业务指标包括分析耗时、异常发现到责任交接时长、建议采纳后完成率，以及经可比观察验证的缺货、延迟、退款和贡献变化。质量指标包括数据映射准确性、证据可追溯性、模型结论人工通过率及权限隔离结果。

立项后先采集基线，再冻结目标值和观察窗。创建采购草稿不计为采购到货；创建工单不计为问题解决。库存资金占用、利润和销售额分别评价，收益不重复计算，不将同期增长直接归因于 AI。

03 范围与系统责任

3.1 首期范围

  • 接入试点所需的授权 ERP、OMS、WMS、CRM、财务和渠道数据；按实际场景最小集合实施，不以“全部系统全量接入”为前置目标。
  • 建立身份映射、数据质量、统一指标、证据快照、权限与审计。
  • 实现 S01—S04 四类分析及跨领域综合；实现统一工作台、预警、建议、审批和结果跟踪。
  • 经审批，仅允许创建 ERP 采购草稿、CRM 内部工单；接口未验证前只提供分析及可导出的建议。

3.2 首期排除

原 ERP/OMS/WMS/CRM/财务系统继续承担商品主账、采购审批、库存记账、分仓出库、退款退货办理、客户沟通和会计核算。首期不新增自动支付、自动退款、库存调整、自动投放、自动调价、自动发布页面或对客发送消息。

第三方仓、独立物流系统、外部市场数据、图关系数据库、视觉质检和自动执行优化动作均按单独需求评审，不能因为流程图包含该业务就纳入交付。

3.3 权威事实

ERP、OMS、WMS、CRM、财务和渠道按数据域确认权威来源。实际一个软件可承担多个逻辑角色。中台保存带来源和时间的分析投影，不成为第二套订单、库存或财务主账。ERP 和 WMS 展示同一仓的库存镜像时不得相加；自营仓与平台履约仓分开核算。

04 自上而下的逻辑架构

本草案采用五层逻辑分层，并设置贯穿各层的治理能力。分层用于定义依赖与职责，不等同于五个独立部署系统。首期采用模块化单体加异步任务执行器；出现独立扩缩容或隔离需求后再拆服务。

层级 组成 职责与依赖边界
L1 体验与接入层 W01 统一工作台、API 入口 统一查询、分析报告、建议及审批入口；不在页面重复计算业务指标
L2 场景与任务编排层 S01—S10 场景插件、O01 任务编排 O01 选择、调度场景并综合结果；场景声明领域需求、执行业务步骤并调用公共能力
L3 通用能力层 B01/B02 领域计算；A01—A03 通用智能；C01—C03 协同控制 提供唯一的计算、模型、理解、检索、建议、审批与执行实现；通用智能与协同写入互相隔离
L4 数据与集成层 D01—D04 接入、映射、投影、质量、快照和证据；以标准数据契约隔离厂商差异
L5 运行基础层 I01 持久化、任务恢复、凭据引用与必要运行承载 依据实际需求选择技术实现；文件、检索与队列能力按需使用，不先建通用接口体系

4.1 允许的依赖

体验入口 → 场景应用 → 通用能力接口 → 标准数据端口/基础设施适配器。业务规则依赖抽象，不直接依赖模型品牌、ERP 厂商 SDK、数据库驱动或工作流产品。

统一场景任务路径为 W01 → O01 → 所选 ScenarioHandler → B01/B02/A01—A03 等公共能力 → 场景领域结果 → O01 综合报告。O01 不绕过场景重新执行领域计算、分类或领域检索；场景不反向调用 O01 调度其他场景。跨领域参与者由 O01 依据依赖和权限选择，通过同一固定数据输入及结构化结果综合，不互调私有实现或互写数据。

O01 可调用 D03 协调输入快照、D04 校验证据引用，以及 A01/A03 完成明确标为“联合报告”的解释或补证，不重复场景已完成的领域步骤。统一查数入口 W01 → A03 是独立受控查询；需要场景分析时仍进入上述任务路径。A03 可调用 B01 的受控指标查询，不复制公式。C03 独占外部业务写端口，模型工具集合不包含这些端口。

模块实现可同进程部署，但禁止跨模块直接读写私有表；通过公开服务契约、只读投影或版本化事件交换数据。

4.2 开闭原则的具体落实

稳定内核包含权限、快照、指标执行、任务状态、审批和幂等执行。不将具体场景名写成核心服务中的连续条件分支。变化部分通过已审核的接口实现与注册清单接入。

每项扩展需声明标识、版本、输入输出模式、所需数据域、工具白名单、权限、预算和支持的动作类型，并经过契约与回归验证。首期采用代码注册、依赖注入或受控配置，不提供任意用户上传代码的插件市场。

开闭原则不意味着核心永不修改：出现新的业务不变量或权限模型时，允许评审并演进核心契约；不得用任意 JSON 字段和通用执行脚本绕过必要设计。

05 需求去重与唯一归属

5.1 去重规则

  1. 一个业务事实或指标只有一个权威定义；各场景按版本引用。
  2. 一个可复用能力只有一个模块负责人、公开接口和持久化写入归属。
  3. 场景保留独有的业务目标、约束、证据清单和方案模板，不复制通用引擎。
  4. 预测结果、投诉标签和知识片段是派生信息，不能替代原系统事实。
  5. 公共接口、前端组件、物理数据库可共享；聚合统计口径和写入权限不能因共享而混淆。

A01 模型网关 模型适配、结构化输出校验、超时、限额、成本及技术错误状态 只报告模型调用结果，不决定 RULES_ONLY、部分报告或业务阻断，不持有审批权 可替换模型提供方、技术失败信息及成本跟踪
A02 内容理解与抽取 分类、聚类、翻译、结构化字段抽取及置信度 不负责投诉分母、财务公式或权威实体合并 VOC 文本理解；OCR/图像按阶段扩展
A03 检索与受控查询 知识检索、指标查询、必要关系查询及证据引用 先过滤权限再检索；结构化查询经语义计划与只读校验 文本与指标查询；图查询端口预留但不要求首期建图
C01 建议与预警 统一建议模型、风险去重、责任交接、确认及效果关联 不替场景生成业务算法，不拥有批准权 规则预警、建议参数及证据绑定
C02 审批与授权 独立审批、权限和有效期核查、不可变批准版本 不创建采购单，不用模型审校替代人工批准 发起人与审批人分离；变更参数使旧批准失效
C03 受控执行与结果跟踪 独占外部写入调用、幂等键、回执核对及业务结果关联 仅消费有效批准；执行成功与业务完成分开存储 ERP 草稿、CRM 内部工单两类动作
G01 权限与策略 身份、角色、企业/店铺/仓库范围和工具策略 在服务端独立执行；缓存与索引同样受控 默认拒绝、最小权限、敏感字段保护
G02 审计、观测与评测 操作链路、模型/规则版本、质量样本、运行指标及评测结果 运行日志不等于业务主账；不无差别记录敏感内容 全链路追踪、规则基线和模型评测集
I01 运行基础 实际需要的数据持久化、任务领取/恢复、凭据及日志备份承载 不实现业务判断；不预先定义万能 Repository、Index、Queue、Blob 等接口族 模块化应用与 Worker，复用现有存储/运维；文件和检索按实际需求选择实现

6.1 O01 内部分工与业务降级

O01 内部承担五项职责：接收任务并选择参与场景；维护计划、依赖与预算；协调 D03 输入快照及受影响重跑；综合领域结果并按必需/可选依赖决定整体业务状态；审校引用并发布报告版本。这些是同一逻辑模块内的分工，不新增模块编号、独立服务或通用引擎。

场景负责领域内的步骤依赖、业务规则和失败影响判断，并把可用产物引用、缺失能力及被阻断的业务结论返回 O01。A01 仅返回模型调用成功或 TIMEOUT、RATE_LIMITED、UNAVAILABLE、INVALID_OUTPUT 等技术错误信息；这些是示例技术类别，不是业务终态。A02/A03 保留能力结果或失败原因，不替场景决定采购、售后等业务可否继续。

场景先确定本领域可用结果及业务限制，O01 再依据请求目标和必需/可选参与者形成完整、部分、RULES_ONLY 或阻断的报告状态。规则结果可用不代表缺失的质量信号为安全；依赖该信号的业务结论与后续建议必须阻断。业务降级规则归场景及 O01 的相应编排职责，不能由模型提供方错误码直接推出。

07 首期场景功能需求

7.1 S01 供需与库存分析

  • S01-01 范围与证据：用户选店铺、仓库、SKU、分析时点及窗口，获取 OMS 需求、WMS 可售、ERP 未收供给、供应约束及 CRM 质量信号。缺映射、供给重复或关键库存过旧时阻断可执行补货建议。
  • S01-02 计算与推演：S01 调用 B01 计算给定输入下的逐日余额、首次缺货日、目标缓冲和缺口；调用 B02 形成预测/候选数量及到货安排，B02 对各候选复用 B01 评价。分别处理 MOQ、订购倍数及预计可售日，避免重复扣减已预留需求或将到港当可售。
  • S01-03 联合判断：S01 返回供需领域结果及所需质量依赖，O01 按任务计划调度 S03 并综合两域结果，比较常规采购、加急协调、先调查等路径；S01 不反向调度 O01。超出业务依据时展示待确认事项，不编造交期或供应商承诺。
  • S01-04 输出：提供数量、日期、逐日曲线、关键假设、证据和替代方案。质量达到调查阈值或关键数据未满足条件时，禁止转采购草稿，可形成调查建议。
  • S01-05 动作：只读报告先输出采购候选方案；用户选择后经 W01 生成 C01 采购草稿建议，后续确认、审批和执行分别使用 C01/C02/C03。

7.2 S02 履约风险分析

  • S02-01 关联：关联订单、承诺发货/交付时间、仓库作业、多个包裹及客户催单；保持订单与包裹粒度差异。
  • S02-02 识别：确定性规则识别超承诺、未出库、物流停滞等情况；迟到事件不能覆盖更新状态。
  • S02-03 解释：结合库存、仓内状态和物流事件列出已证实事实、候选原因、责任线索和待调查差异。相关性不能表述为已证明原因。
  • S02-04 输出与动作：按影响和紧急度排序，复用 C01 去重及 C02/C03 创建内部履约工单；不分仓、取消订单、改地址或补发。

7.3 S03 客户体验与 VOC 分析

  • S03-01 理解：A02 对授权脱敏反馈进行主题提取，保留原文证据、语言、置信度和 UNKNOWN 分类；人工修正形成有版本的标签记录。
  • S03-02 统计：B01 按店铺、SKU、成熟签收群组和观察窗计算去重投诉订单占比，分别显示工单数、订单数及样本量。
  • S03-03 关联：关联页面描述、履约、退款及已有质检记录；区分商品、物流、描述及服务主题，不从投诉直接认定缺陷。
  • S03-04 输出与动作：输出主题趋势、重复问题、证据及调查候选方案；质量信号通过 O01 领域结果或已发布结果引用供其他场景使用，不直接调用 S01；用户选择生成业务建议后，复用 C01—C03 的确认、审批及内部调查工单流程。

7.4 S04 贡献与费用分析

  • S04-01 取数：统一订单实收、成功退款、费用、商品成本、财务确认成本转回和币种，区分估算、实际及数据覆盖状态。
  • S04-02 计算：B01 按适用且已确认的口径计算贡献；累计账单取最新有效版本，增量事件按唯一记录汇总，适配转换规则留痕。
  • S04-03 解释：分解销量结构、退款、平台费、履约费等变化；广告未归因到订单时只做有依据的期间分析。
  • S04-04 输出与动作：缺少必要费用时输出部分结果及缺项，不填零；贡献不标为净利润。可建议内部财务核查，不修改账目。

7.5 统一分析输出

四类场景均通过同一结果协议输出：分析范围、数据事实时点及覆盖情况、指标及版本、已确认事实、候选原因、备选方案、风险、不确定性、证据引用、建议动作及追踪标识。模型推断、程序计算和原始事实使用不同类型标识。

该 JSON 是受理后的逻辑契约样例，不是新增接口实现；不含真实业务数据。SINGLE 使用完全相同的结构，participants 恰有一个参与者；JOINT 至少两个，可按预算分批调度，不限制总参与者必须等于并行度。每个 participantId 唯一，场景版本、必需/可选属性和参数依据获准模板由 O01 校验；用户不能把强制的质量依赖改成可选。版本为示例，并不表示所有场景已经部署。

SINGLE/JOINT按实际执行的场景参与者数区分，不按来源系统数量区分。单场景可引用满足时效和口径的已发布领域结果；若必须新增另一个场景执行分析，O01须显式纳入participants并记录为JOINT，不允许隐藏参与者。规划后发生此类变化按计划版本和有效重规划预算处理。

scope 是可信授权范围的共同边界；参与者仅能在其子集取数。window.asOf 是共同观察锚点，业务观察窗口分别由参与者参数/模板定义，例如 S03 成熟群组窗口不能被 S01 的7天需求窗口替代。D03 根据全部已选参与者的数据需求形成统一输入清单。

planVersion 受理时可空，由 O01 形成计划后赋值；snapshotId 冻结前可空，由 D03 赋值。实际分析前两者必须确定。O01 向每个场景下发该计划中的参与者视图，包含 taskId、planVersion、participantId、场景版本、获准范围/参数、snapshotId、策略引用及分配预算；这不是第二套独立任务上下文。DomainResult 必须带参与者、计划和快照引用，报告不能混合不兼容的输入版本。

tenantId、policyContextRef 和有效预算由服务端生成或校验，不能因用户提交字段而扩大权限。任务冻结所用场景、指标、理解/模型及策略版本引用；各版本定义仍由原归属模块维护。报告证据必须能在当前访问者权限下解析。旧的根级 scenarioId/scenarioVersion 仅适合单场景的假设不再作为本版 AnalysisContext 使用。

8.2 扩展兼容规则

接口包含 schemaVersion；允许经过验证的可选字段扩展，删除字段或改变语义必须发布新主版本。任务保留旧版本依赖。注册清单声明兼容范围，升级经过固定样本回归、灰度和回滚验证。

工具仅为受控能力包装，MCP 等协议是接入形式，不创建第二套业务逻辑或授权体系。Skills 是版本化方法和模板，不允许携带绕过控制的任意代码。Memory 只保存经确认可撤销的偏好，不把过期库存、费用或审批结果长期当成事实。

8.3 可配置任务预算

maxDomainParallelism 为同时运行的领域场景数，默认2，正整数；maxReplans 为单任务整体重规划次数，默认1，非负整数。默认值用于初始试点，不是固定产品上限或所有任务必须耗尽的额度。单场景实际并行度为1，多于两个参与者时可分批运行。

有效参数由 O01 依据获准任务配置、G01 策略约束及运行预算校验，按 budgetPolicyVersion 随任务冻结。工具次数、时长、费用等仍须有界，其具体限额待容量和质量评估确认，不在本文新增无依据数值。普通用户及模型不能自行放宽限额。

改变参与者/任务依赖或纳入原快照以外的数据并重跑计入重规划；原计划/快照内的检索按工具和时长预算控制，不另算一次重规划。补证和审校引发的重规划共用 maxReplans，不各自获得新额度。调整依据包括来源/模型限流、任务时延、费用、资源、失败率及评测质量；配置变更用于后续任务，不静默改变历史任务的有效预算。

9.2 关键口径

  • 可售：在来源分桶可可靠转换且互斥的前提下，available = onHand − reserved − frozen − unusable。原始字段、转换规则和差异均保留。
  • 未来供给：只计所选范围内符合条件的未收供给，按预计可售日进入模拟；已收部分不得继续作为未收供给。
  • 投诉占比：分子为匹配范围内去重投诉订单数，分母为同一成熟签收群组的订单数；不能与工单数或已证实缺陷率混用。
  • 贡献：按确认口径将实收、退款、费用、商品成本及财务成本转回组合；缺项显式标记，不能替代净利润或银行到账。
  • 时间：分别保存 sourceUpdatedAt、asOf、observedAt、coverageThrough；按数据域配置可接受时效，不统一套用一个阈值。

10 端到端分析与动作流程

10.1 只读分析链

用户选定问题及范围 → G01 鉴权 → O01 形成参与者与任务计划并协调 D03 固定输入 → O01 调度各 ScenarioHandler → 场景按业务依赖调用 B01/B02/A01—A03（B02 情景评价复用 B01）→ 场景返回领域结果引用与业务限制 → O01 完成联合补证、业务状态判定、综合与审校 → W01 展示已发布报告及候选方案。D01/D02 在公共数据链提供授权事实；O01 不另跑一套领域步骤。

步骤按可配置预算和业务依赖调度，不能跳过质量或权限检查。补证超出原快照时，由 D03 创建新输入版本，O01 在允许额度内组织受影响场景重跑或验证可复用结果兼容性，不混合不兼容版本。模型失败由 A01 返回技术错误；场景和 O01 分别决定领域限制与整体报告业务状态。

只读分析终点是 O01 发布报告（含完整、部分、RULES_ONLY 或阻断说明）。报告中的候选方案不自动生成 C01 建议、不进入审批或执行。用户明确选择生成业务建议后，W01 使用报告/候选方案引用进入 C01 流程。

10.2 经人工批准的写入链

建议、审批及执行分别启动并有独立终点：用户生成并确认建议 → C01 保存 DRAFT/CONFIRMED；用户明确提交审批 → C02 由另一授权人员决策并保存 APPROVED/REJECTED 等结果；授权人员另行触发执行 → C03 复核权限、版本、证据和来源条件 → 经 ActionAdapter 创建原系统草稿/工单并记录执行结果。后续业务结果关联是跟踪，不是上述流程自动连通或已完成业务的证明。

AI 的审校通过只表明内部检查完成，不是业务批准。执行器不接受模型直接提交的批准结果。

10.3 状态与幂等

  • 建议状态只由 C01 维护：DRAFT、CONFIRMED、SUBMITTED、SUPERSEDED、CANCELLED；审批状态只由 C02 维护：PENDING、APPROVED、REJECTED、EXPIRED、REVOKED。两者通过 suggestionId 和 suggestionVersion 关联，不共用一个可被双方写入的状态字段。变更关键参数、证据或范围必须生成新建议版本，旧批准不得用于新版本。
  • 执行状态由 C03 管理：READY、SENDING、SUCCEEDED、FAILED、UNKNOWN。一次逻辑动作使用同一 executionKey；请求指纹变化不能复用旧批准。
  • 超时或回执丢失进入 UNKNOWN，先以原键查询。只有适配器提供权威未创建结论且声明可安全重试，才允许以原键重试；禁止换新键绕过未知状态。
  • Worker 租约过期不证明外部动作未发生；SENDING 恢复时先核对回执。原系统不支持可靠幂等或查回执时，该写入适配器不得进入首期上线范围。
  • SUCCEEDED 表示草稿或工单已创建。原系统后续驳回、到货和问题解决分别作为业务结果，不篡改曾成功创建的执行事实。

11 典型扩展示例

11.1 新增物流到货预测

在 D01 注册已授权物流连接器；D02 增补标准事件映射；B02 注册到货预测提供方；S02 增加预计到仓/可售风险模板与特征；复用 W01、D03/D04、C01—C03。若只增加分析，无须修改审批执行内核或另建通知系统。

11.2 新增单证核对

在 A02 注册文档抽取提供方，D04 保存字段证据位置；S07 定义发票、装箱单等业务交叉校验；复用现有来源存储、权限、人工复核组件及内部工单。OCR 不直接写 ERP，不把抽取内容自动确认为主数据。

11.3 更换模型提供方

实现 A01 的 ModelProvider 并注册能力和预算，运行固定评测集，通过后灰度启用；S01—S04 不应修改厂商 SDK 调用代码。结构化模式或输出能力不兼容时明确降级，不静默伪装同等能力。

11.4 新增外部动作

新增自动退款或调价不是添加一个工具即可开放。需独立评审业务规则、权限、审批、幂等及恢复契约，在 C03 注册新动作类型并补充验证；首期两类动作的白名单保持明确。

12 研发拆分与防重复开发约束

建议按逻辑包组织，而非按 22 个候选场景分别建设系统：

apps/              # W01 页面、API 入口及后台任务宿主
scenarios/         # S01—S04 首期；后续 S05—S10 插件
orchestration/     # O01 任务、综合、审校、预算
capabilities/      # B01/B02、A01—A03，各有公开端口
collaboration/     # C01—C03 建议、审批、执行
data/              # D01—D04 标准事实、质量和证据
governance/        # G01/G02 权限、审计、评测
adapters/          # 外部系统、模型、索引和存储实现
contracts/         # 版本化模式、端口和事件；不放业务大杂烩

此结构是建议，不限定语言或框架。实体类型靠近归属模块，contracts 只放公开数据契约，避免形成被所有模块随意修改的“公共工具包”。

需求评审时新增条目必须填写：主归属模块、所复用能力、确实新增部分、输入输出、动作边界、验收样例和阶段。发现相同输入、输出及规则时合并为同一能力；仅页面文案不同不能立新服务。

提交代码或设计评审至少检查：场景无厂商 SDK 直连；无跨模块私表写入；无重复指标公式；无独立场景审批/执行表；结构化查询只读且带服务端范围；公共契约变更有兼容策略。G02 用代表性样例验证新扩展不破坏已有四类场景。

13 非功能需求与降级

编号 要求 验收方式
NFR-01 权限隔离 企业、角色、店铺、仓库及字段范围在查询、检索、缓存、导出和执行均生效；撤权后结果不可继续通过旧缓存访问 正反向权限样例、越权及撤权验证
NFR-02 证据可靠性 报告引用存在、可解析且有权限；缺失引用不能支持确定结论；原始内容变更保留版本策略 抽样解析、断链和来源变更验证
NFR-03 外部内容隔离 客服文本、网页及单证属于数据，不得改变工具白名单、授权或审批；敏感字段按需脱敏 提示注入、恶意文档及工具越权样例
NFR-04 可恢复执行 去重、幂等键、回执和租约恢复保证外部动作不因重试重复创建 故障注入及源系统实际结果核对
NFR-05 有界运行 每任务冻结有效预算及配置版本；领域并行度默认2、重规划默认1且可按第8.3节调整，工具/时长/费用仍有界 默认值、不同参与者数、配置变更、超预算和循环调用样例
NFR-06 可解释降级 A01仅返回技术错误；场景按领域依赖决定限制，O01综合决定部分、RULES_ONLY或阻断等业务状态；关键证据缺失不得当作安全 同一技术错误在必需/可选依赖下的不同业务结果，及来源过旧验证
NFR-07 性能与容量 分别度量交互查询和异步分析的时延分位数、队列等待、吞吐与成本 冻结数据规模和并发画像后压测；目标值由项目评审确认
NFR-08 运维恢复 监控来源延迟、质量异常、模型失败、执行未知和积压；可备份、恢复及回滚 恢复演练；RPO/RTO 按业务影响评审冻结
NFR-09 评测治理 规则计算用确定样例，模型用业务金标准与人工复核；版本升级需回归 场景正确性、引用、未知处理和成本联合评测

性能、可用率和存储周期不在缺少规模依据时给出承诺值。企业需在详细设计前确定容量、数据留存、部署位置和外部模型数据使用条件。

AC-08 累计账单 同一订单累计结算快照从20变37.23 取最新37.23，不相加；缺费用时显示部分结果 D01/D02/B01

AC-12 降级与扩展 模型不可用；再替换一个模型或连接器实现 A01返回技术错误；场景/O01依据必需依赖分别限制领域/整体结果，可用规则结果不等于质量安全；提供方替换不改指标口径 A01/O01/相应场景/D01/G02

以上数字来自指南的演示口径或其直接组合，不是企业实测结果。补货推演按D0后7天、新增需求和所列可售日期执行。模型主题、解释和方案采用业务金标准人工评估，评分阈值在试点前冻结，不以单一模型自评分代替验收。

R01—R09复核还应检查：SINGLE与JOINT使用同一上下文结构；3个以上参与者在有效并行度内分批运行；O01没有旁路领域计算；只读任务不生成建议/审批/执行记录；改变快照、计划或报告只更新相应拥有者；I01不因接口预留而要求新增技术组件。这是文档一致性验收补充，不是本次启动代码开发或新增测试工程。
