>

## 01 设计口径与阅读说明

### 1.1 保持原分层与编号

需求文档采用五层逻辑架构。本文件将 L2 的“场景层”和“任务编排层”分别展开，二者仍同属 L2，不重新编号为六层。基础设施层对应原 L5“运行基础层”。

| 需求文档层级 | 本文件展开方式 | 模块编号 |
|---|---|---|
| L1 体验与接入层 | 工作台及 API 入口 | W01 |
| L2 场景与任务编排层 | 场景层 + 任务编排层，分别展示 | S01—S10；O01 |
| L3 通用能力层 | 领域计算、通用智能、协同控制 | B01/B02；A01—A03；C01—C03 |
| L4 数据与集成层 | 接入、身份投影、质量快照、证据血缘 | D01—D04 |
| L5 运行基础层 | 基础设施适配与承载 | I01 |
| 横向治理 | 全链路权限、审计、观测和评测 | G01/G02 |

图中的“原系统”“模型提供方”“ActionAdapter”“数据库”等不增加新的公共模块编号。端口、适配器、存储和 Worker 是实现角色，不能与业务模块数量直接等同。

### 1.2 图示语义

- 总体逻辑图展示职责、主要调用和受控边界，省略重复的返回箭头；完整数据方向见数据流图。
- 时序图展示代表性调用顺序，参与者是逻辑职责，不代表网络进程。并行领域分析最多两个，补证/重规划共用一次额度。
- 数据流图中实线表示业务数据或产物，虚线表示调度、授权、校验或运行支持。
- 标记 P1/P2 的场景和技术选项表示可分期实现，不代表现已上线或首期必须部署。
- 所有图使用 Mermaid 基础 flowchart/sequenceDiagram 语法；图源与离线 SVG 随文提供。语法参考：[流程图](https://mermaid.js.org/syntax/flowchart.html)、[时序图](https://mermaid.js.org/syntax/sequenceDiagram)。

### 2.1 架构约束

1. O01 调度任务，场景维护业务意图、特征和方案规则；A01 不接管任务状态，B01 不接管审批。总体图使用层和能力组之间的关联表达分工；运行时W01提交O01，领域专有步骤由所选ScenarioHandler调用公共端口。详细调用见时序图及第07节，不再重复执行另一套计算。
2. 模型调用统一经过 A01；金额、库存、分母和供需模拟由 B01/B02 执行。模型可建议查询，服务端必须验证权限和只读计划。
3. D02 不重建原业务主账；D03 固定输入，D04 保存引用和血缘，不成为混合存放全部事实的新“万能数据库”。
4. 只有 C03 可触达外部业务写入端口；D01 是读取同步能力。ActionAdapter 由 C03 注册和调用，不能被 A01/A03 当作工具直接使用。
5. G01/G02 覆盖图中全部调用边界。图中虚线连接是治理作用示意，不表示依靠一次入口鉴权即可信任后续调用。
6. 图中模型提供方、存储和索引是可替换实现；并不要求企业同时部署本地模型和云模型。

## 03 共性流程一：跨领域只读分析

以“某 SKU 是否补货，同时客户投诉上升”为代表：O01 选择 S01 与 S03，共用一个快照；最多两个领域并行，领域结果返回 O01 综合。其他场景替换 ScenarioHandler 和必要证据，不复制任务、指标、模型、检索或报告链。

```mermaid
sequenceDiagram
  %% diagram: 02-cross-domain-analysis
  autonumber
  actor U as 业务人员
  participant W as W01 工作台
  participant G as G01 权限策略
  participant O as O01 任务编排
  participant Q as D03 质量与快照
  participant S1 as S01 供需与库存分析
  participant S3 as S03 客户体验分析
  participant B as B01 指标计算
  participant F as B02 预测与优化
  participant T as A02 内容理解
  participant R as A03 检索查询
  participant M as A01 模型网关
  participant E as D04 证据血缘

  U->>W: 提出问题，选择店铺、仓库、SKU及窗口
  W->>G: 校验身份与对象范围，生成可信策略上下文
  G-->>W: 授权范围或拒绝
  break 权限拒绝
    W-->>U: 拒绝请求，不创建越权分析
  end
  W->>O: AnalysisContext + policyContextRef
  O->>Q: 检查场景所需数据域并创建快照
  Note over Q,E: D03经D02公开端口校验投影版本，并读取D01覆盖水位<br/>D04登记可追溯证据引用，不复制业务主账
  alt 关键数据不达标
    Q-->>O: 缺映射、过旧、覆盖缺失或供给矛盾
    O-->>W: 阻断相关结论和可执行建议，列待补事项
    W-->>U: 展示已确认的有限信息
  else 数据满足分析条件
    Q->>E: 登记冻结输入与快照血缘
    Q-->>O: snapshotId + manifest + 版本与覆盖信息
    par 同一快照，领域并行一
      O->>S1: analyze(context, snapshotId)
      S1->>B: 需求、可售、未收供给、采购约束
      B->>E: 登记指标结果及来源链
      B-->>S1: 带版本的确定性指标
      S1->>F: 逐日余额与候选方案模拟
      F-->>S1: 缺货日、补货量、交期及约束结果
      S1-->>O: 供需领域结果与证据
    and 同一快照，领域并行二
      O->>S3: analyze(context, snapshotId)
      S3->>T: 对授权脱敏反馈分类与提取主题
      opt 使用语言模型提供方
        T->>M: 受结构化模式与预算约束的理解请求
        M-->>T: 标签、置信度或明确失败状态
      end
      T-->>S3: 主题结果、原文引用、UNKNOWN项
      S3->>B: 按成熟签收群组去重计算投诉占比
      B-->>S3: 分子、分母、窗口、指标版本
      S3-->>O: 体验领域结果与调查信号
    end
    O->>R: 检查证据缺口并执行允许的补查
    R->>G: 再校验知识、字段和对象范围
    R->>E: 按当前权限检索并解析引用
    E-->>R: 证据或缺项，不返回越权内容
    R-->>O: 有权限的补证结果与范围限制
    opt 补证超出原快照且尚有一次重规划额度
      O->>Q: 创建新的固定输入版本
      Q-->>O: 新snapshotId，不修改旧快照
      O->>S1: 用新快照重跑受影响的供需分析
      S1-->>O: 同版本领域结果
      O->>S3: 用新快照重跑受影响的体验分析
      S3-->>O: 同版本领域结果
    end
    O->>M: 综合证据、比较方案、说明不确定性
    alt 模型可用且结果通过审校
      M-->>O: 结构化解释与候选建议
    else 模型失败或输出无法验证
      M-->>O: RULES_ONLY或明确失败状态
      Note over O,M: 仅返回已确认的规则结果；缺失质量信号不可当作无风险<br/>依赖该信号的采购建议必须阻断
    end
    O->>E: 校验报告引用存在、版本匹配及访问范围
    E-->>O: 引用校验结果
    O->>O: 保存领域结果、综合报告、版本和预算用量
    O-->>W: 报告、证据、限制和未批准候选建议
    W-->>U: 展示分析，不改变原系统事实
  end
  Note over W,E: G02贯穿记录任务、模型、规则、证据、费用与降级；任一模型调用均有超时及失败处理
```

**复用边界：**B01 统一计算投诉分母和库存；B02 负责模拟；A02 只理解内容；A03 只检索或执行受控查询；O01 持有任务、领域结果及报告。S01/S03 不互调私有服务，也不各自生成独立审批流程。以上“无风险”必须由足够证据支持，不能由模型故障的空结果推断。

## 04 共性流程二：业务建议与人工审批

S01 的采购草稿建议、S02 的履约工单建议、S03 的质量调查建议和 S04 的财务核查建议均使用同一套 C01/C02 流程，仅动作类型、参数模式、业务规则和审批策略不同。

```mermaid
sequenceDiagram
  %% diagram: 03-suggestion-and-approval
  autonumber
  participant O as O01 任务编排
  actor U as 建议发起人
  participant W as W01 工作台
  participant C1 as C01 建议与预警
  participant C2 as C02 审批与授权
  participant G as G01 权限策略
  participant Q as D03 质量与快照
  actor H as 另一授权审批人

  O->>C1: 报告引用、风险键、候选动作与参数模式
  C1->>C1: 风险去重，保存DRAFT建议版本和证据绑定
  C1-->>W: 待确认建议与业务依据
  U->>W: 核对具体数量、日期、范围和证据
  W->>G: 校验确认和发起权限
  G-->>W: 允许或拒绝
  alt 发起权限不足
    W-->>U: 拒绝提交
  else 允许发起
    W->>C1: 确认suggestionId、suggestionVersion及参数指纹
    C1->>Q: 检查建议依赖数据与快照是否仍适用
    Q-->>C1: 有效或需要刷新
    alt 关键证据失效或参数不完整
      C1-->>W: 不进入审批，要求补证或生成新分析
    else 建议满足提交条件
      C1->>C1: DRAFT到CONFIRMED
      C1->>C2: 提交不可变建议版本和批准范围
      C2->>G: 校验动作类型、审批策略和人员分离要求
      G-->>C2: 可审批范围与允许审批人
      C2->>C2: 创建PENDING审批记录
      C2-->>C1: 审批请求已受理
      C1->>C1: CONFIRMED到SUBMITTED
      C2-->>W: 待审批任务、参数指纹和有效期
      H->>W: 查看证据并批准或拒绝
      W->>C2: 提交人工决策及意见
      C2->>G: 再校验当前权限、范围与独立审批人身份
      C2->>C1: 读取被批准建议的准确版本
      C2->>Q: 复核证据适用性及有效期
      alt 校验通过且人工批准
        C2->>C2: 写入APPROVED及批准参数指纹、版本和有效期
        C2-->>W: 有效批准记录，不代表已执行
      else 人工拒绝
        C2->>C2: 写入REJECTED及意见
        C2-->>W: 拒绝结果
      else 权限、版本或证据已变化
        C2-->>W: 不批准，要求刷新或重新提交
      end
    end
  end
  opt 后续修改数量、范围或关键证据
    U->>W: 修改建议
    W->>C1: 创建新建议版本
    C1->>C1: 原版本SUPERSEDED，新版本重新确认
    C1->>C2: 失效通知及旧版本关联
    C2->>C2: 撤销相关批准或保留过期记录，旧批准不得用于新版本
  end
  Note over C1,C2: 建议状态仅C01写入；审批状态仅C02写入<br/>通过suggestionId和suggestionVersion关联，不共写状态字段
  Note over O,H: AI审校不等于人工批准；G02记录发起、确认、审批和版本变化
```

**状态一致性：**C01 拥有 DRAFT、CONFIRMED、SUBMITTED、SUPERSEDED、CANCELLED；C02 拥有 PENDING、APPROVED、REJECTED、EXPIRED、REVOKED。工作台聚合显示，不复制一套场景专用审批台账。

## 05 共性流程三：受控执行、未知恢复与业务结果

执行流程只允许 C03 使用 ActionAdapter。首期动作类型仅为 ERP 采购草稿、CRM 内部工单；图中的外部系统可为同一企业现有系统，不代表另建业务平台。

```mermaid
  C3->>G: 校验当前执行权限、范围及动作白名单
  G-->>C3: 授权结果
  break 当前执行权限或动作白名单不满足
    C3-->>W: 拒绝执行，不读取外部前置条件或提交写入
  end
  C3->>C2: 读取有效批准、参数指纹、有效期和撤销状态
  C2-->>C3: 不可变批准版本或无效原因
  C3->>C1: 读取该建议的准确版本与状态
  C1-->>C3: 建议版本及动作参数
  C3->>Q: 复核证据时效、输入版本与适用条件
  Q-->>C3: 有效或需要重新分析
  break 批准、建议版本或证据无效
    C3-->>W: 拒绝执行，要求刷新或重新审批
  end
  C3->>A: 校验来源当前前置条件
  A->>X: 授权读取供应、商品、对象状态等必要条件
  X-->>A: 当前条件与来源版本
  A-->>C3: 前置条件校验结果
  alt 任一授权、批准、版本或当前条件不满足
    C3-->>W: 拒绝外部提交，列原因及刷新要求
  else 允许提交
    critical C03本地原子保护，不是跨系统分布式事务
      C3->>C3: 绑定逻辑动作、批准版本、请求指纹与executionKey
      C3->>C3: 唯一约束及状态比较，防止并发重复发送
    end
    C3->>C3: READY到SENDING，保存发送意图
    C3->>A: execute(executionKey, approvedPayload)
    A->>X: 创建采购草稿或内部工单，同一幂等键
    alt 明确创建成功
      X-->>A: 外部单号及确认回执
      A-->>C3: 已确认创建结果
      C3->>C3: SUCCEEDED，保存外部ID和回执
    else 权威确认未创建且本次失败
      X-->>A: 明确未生效的错误
      A-->>C3: 已确认失败类型
      C3->>C3: FAILED，保留原键与失败依据
    else 超时、断连或响应丢失
      A-->>C3: 无法确认是否已生效
      C3->>C3: UNKNOWN，不生成新executionKey
      C3->>A: queryReceipt(原executionKey)
      A->>X: 查询原键对应结果
      X-->>A: 已存在、权威未创建或仍不确定
      alt 查到原外部单号
        A-->>C3: 确认已创建
        C3->>C3: SUCCEEDED，补记同一动作结果
      else 权威NOT_FOUND且适配器保证可安全重试
        A-->>C3: 未创建依据与安全重试能力
        C3->>C3: 重新核查有效批准、权限、条件及重试预算
        C3->>A: 仍有效时用原executionKey重试
        Note over C3,X: 重试仍按相同回执分支处理，不直接假定成功
      else 查询仍不确定或无安全重试保证
        A-->>C3: 维持UNKNOWN及待核原因
        C3-->>W: 待调查，不允许换键重复创建
      end
    end
    C3-->>W: 当前执行状态、外部单号或待核事项
    opt 已确认创建，且后续业务投影已同步
      Note over X,D: 后续批准、到货、工单办理仍在原系统发生<br/>D01读取后由D02形成带来源时间的业务投影
      C3->>D: 按外部ID和权限读取后续业务结果
      D-->>C3: 原系统状态、事实时点与证据引用
      C3->>C3: 记录业务结果关联，不改写曾成功创建的事实
      C3-->>W: 分开展示执行状态与业务状态
    end
  end
  Note over W,D: G02追踪全过程；Worker租约过期不证明外部未执行<br/>恢复SENDING或UNKNOWN时先按原键核对回执
```

**执行前条件的准确性：**D03 的分析快照不能代替原系统当前条件校验。适配器若能在提交时做条件版本校验，应将前置版本/指纹随提交发送；若无法排除校验与提交之间的变化，必须记录剩余不确定性并按动作风险评审。缺少可靠幂等或回执查询保证的写入适配器，不进入首期上线范围。

**执行状态归属：**READY、SENDING、SUCCEEDED、FAILED、UNKNOWN 仅由 C03 维护。批准失效由 C02 维护；模型和 Worker 不自行授予批准。SUCCEEDED 只表示草稿/工单创建成功，不表示采购已获批、商品已到仓或客户问题已解决。

### 6.1 数据流的关键限制

- 图中“经数据端口读取固定版本”必须结合 D03 的快照清单，通过 D02/D04 公开契约取数，不允许业务模块查询对方私有表。
- A03 的结构化查询经过语义层、只读校验和服务端范围过滤；指标结果仍由 B01 计算。索引不能绕过证据权限和撤权处理。
- A01/A02 的输出是派生解释或标签；只有原系统记录和已确认口径才提供相应业务事实。所有报告区分事实、计算和推断。
- ART 为图示分组，不是一张全模块共写的产物表；B01、B02、A02 各有自己的数据写入边界。
- I01统一承载图中逻辑数据资产；此处不为每个资产再绘制一条物理存储连线。物理部署见第09节，权限和审计仍在各模块边界强制执行。
- ActionAdapter 的结果先返回 C03 服务边界，再由 C03 持久化 EXEC；适配器不能直接写执行台账。
- BAD 保存质量问题与引用，原始内容和标准投影不被静默改写。人工纠正映射后生成新版本并重跑受影响分析。
- C02 的批准、C03 的创建回执、D01/D02 读到的后续业务状态是三种不同证据；不能相互替代。

| AnalysisContext | taskId、scenarioId/Version、scope、window、snapshotId、policyContextRef、budget | scope与身份由服务端校验；首期最多两个领域并行、一次重规划 |

| MetricResult | metricId/Version、值、单位/币种、维度、窗口、分母、缺项、证据、snapshotId | 禁止“同名不同义”和缺项填零；AI只能引用结果 |
| DomainResult / AnalysisResult | 事实、指标、推断、候选方案、限制、证据、版本和建议动作 | 领域结果只返回O01；公开复用通过已发布结果，不能互写私有表 |
| Suggestion / ApprovalRecord | 建议ID及版本、参数指纹、范围、证据、主体、有效期、批准/撤销记录 | C01/C02分别唯一写入状态；新参数不能消费旧批准 |
| ExecutionRecord | executionKey、逻辑动作标识、批准版本、请求指纹、状态、外部ID、回执和业务结果引用 | C03唯一维护；并发提交由唯一约束和状态比较阻止重复 |
| 版本化事件 | eventId、schemaVersion、producer、tenantId、aggregateId/Version、occurredAt、traceId、payloadRef | 单一生产者；消费者去重。使用进程内事件或数据库任务/Outbox即可，不要求首期部署消息中间件 |

工具调用、MCP、Skills、Memory 是复用方式，不新增平行业务引擎。MCP 不替代 G01；Skills 是版本化方法模板；Memory 只保存经确认可撤销的偏好，不永久缓存昨天的库存或批准作为今日事实。

## 09 逻辑模块与物理部署单元

### 9.1 首期建议部署映射

采用一个业务应用代码体系，按运行角色启动 API 与 Worker。它们是部署单元，使用同一套模块实现与契约；不是为每个场景或公共模块部署一个微服务。

### 9.2 部署约束与拆分条件

| 对象 | 首期做法 | 何时考虑独立部署 |
|---|---|---|
| S01—S10场景 | 同一应用内注册插件，按阶段启用 | 有独立容量、发布或隔离证据后再评审；不能因场景多就拆服务 |
| O01、B01/B02、A01—A03 | 保持逻辑包与契约；耗时任务在Worker执行 | 模型调用或优化任务需要独立伸缩、专用资源或故障隔离 |
| D01—D04 | 独立模块，按任务运行；避免阻塞交互API | 大规模同步、独立网络边界、持续积压或隔离要求 |
| C01/C02/C03 | 分开职责与数据拥有者，首期可同一代码体系 | 写入风险要求独立凭据/网络边界，或审计与可用性要求需要隔离执行宿主 |
| G01/G02 | 策略与观测统一，不按场景复制 | 优先复用企业身份/监控；专用服务只按真实规模和治理需要建设 |
| 数据存储 | 可共用物理实例，但私有表、写入归属和契约不混合 | 资源竞争、合规隔离、恢复目标或容量有明确分离需求 |

部署角色的数据库凭据、外部凭据和工具白名单应尽量收敛。模块化单体中的语言级接口隔离不等同于进程级安全边界；如写入动作风险要求更强隔离，可将 C03 放到受限执行 Worker，同时继续复用其契约和代码，不拆分全部模块。

## 10 未来能力与按需技术选项

| 未来能力 | 稳定扩展点 | 当前应预留的设计 | 触发后才评估的技术组件 |
|---|---|---|---|
| 学习型销量、交期预测 | B02 Forecast/OptimizerProvider | 截止时点、特征、区间、算法版本与回测接口 | 专用训练/推理服务、特征平台；首期不必部署 |
| 图关系检索 | A03 Retrieval/QueryProvider | 关系查询计划、范围过滤、路径证据格式 | 只有关系查询收益及容量验证后才引入图数据库；可先查关系表 |
| 大规模语义检索 | A03及I01 Index端口 | 权限标签、版本、重建和撤权策略 | 独立向量数据库或搜索集群；不是RAG的必备独立部署单元 |
| 单证抽取与视觉质检 | A02 UnderstandingProvider | 文件/图片引用、字段位置、置信度和人工确认 | OCR服务、视觉模型、GPU；S07/S09实施时按任务评估 |
| 多仓优化与促销模拟 | B02优化提供方、S08约束模板 | 目标函数、业务约束、假设与场景结果 | 专用求解服务或算力池；首期确定性推演即可 |
| 新渠道、第三方仓、物流或市场资料 | D01/D02来源与域适配 | 来源台账、授权、状态映射、单位和权威域 | 获得实际来源和接口后新增连接器，不提前部署TMS/全网爬虫 |
| 大吞吐事件分发 | 版本化事件、I01任务/队列端口 | eventId去重、Outbox/持久任务和可恢复消费 | 消息队列或流平台；数据库任务满足需求时不新增 |
| 本地模型与模型路由 | A01 ModelProvider | 能力声明、结构化输出、预算和失败状态 | 私有推理服务、GPU或多模型路由器；选型后部署 |
| MCP、Skills和受限Agentic检索 | A03/O01/通用工具端口 | 审核注册、版本、权限、预算及停止条件 | 有跨应用复用需求再部署MCP端点，不等同于新增业务服务 |
| 自动退款、调价、投放或对客发送 | C03 ActionAdapter，关联C02策略 | 动作类型、人工授权、幂等、前置条件和回执契约 | 作为新需求单独评审；不是当前已授权或必须开放的功能 |

扩展按“业务需求获批 → 数据和权限具备 → 提供方注册 → 契约与业务回归 → 灰度 → 按需部署”推进。不能从技术清单反推当前必须建设的组件。

## 12 接口演进、评审及一致性约束

1. 注册清单包含标识、版本、输入输出模式、所需域、允许工具、权限、费用/时长预算和建议动作类型；通过审核代码注册、依赖注入或受控配置扩展，不支持任意代码上传。
2. 公共模式携带 schemaVersion。新增可选字段需兼容验证；删除、改名或语义变化发布新主版本。历史任务、报告、批准和执行记录保留原版本依赖。
3. 场景接入前查重：相同取数、公式、理解、审批或恢复逻辑必须复用；只增加业务约束、特征和输出模板。确需新公共能力时，先说明与已有模块的职责差异。
4. 扩展契约验证与业务回归分开：前者验证模式、权限和适配能力；后者验证补货、履约、VOC、贡献的真实样例及未知处理。模型自评分不能代替业务复核。
5. 未冻结项沿用需求草案第16节：接口厂商、权限矩阵、阈值、币种/汇率、数据留存、部署位置、并发和预算、性能质量目标及恢复目标。本文不擅自给出生产承诺值。
6. 本文件不新增首期退款、库存调整、对客发送、自动调价或投放权限。未来动作须单独评审 C02/C03 契约与审批策略。
